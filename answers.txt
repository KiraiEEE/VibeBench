PART 1 — CORPUS AND SAMPLING
================================================================================

--------------------------------------------------------------------------------
Q1. What does "permissive licence" mean in the AIDev filter phase?
--------------------------------------------------------------------------------

It means the repository's licence legally lets you copy, analyse and redistribute
the code — including quoting it in a published thesis — without forcing you to
open-source your own work in return.

Our allowlist (vibebench/config.py :: PERMISSIVE_LICENSES):

    MIT, MIT-0, Apache-2.0, BSD-2-Clause, BSD-3-Clause,
    0BSD, ISC, Unlicense, CC0-1.0, MPL-2.0

What is EXCLUDED and why:

  * GPL / AGPL and other strong copyleft. These are legitimate licences, but
    redistributing or quoting the code carries obligations that complicate a
    published academic artefact.

  * Repositories with NO licence at all — and this is the big one. About 65% of
    AIDev's 116,003 repositories have no licence recorded (only 39,983 have one).
    "No licence" does not mean "free to use": under copyright law it means ALL
    RIGHTS RESERVED. Cloning and republishing that code is legally murky.

So the filter is a legal-safety filter first, and a quality signal second.


--------------------------------------------------------------------------------
Q2. Why Copilot 150 and Codex 150, but Devin 128, Cursor 81, Claude Code 37?
    Isn't that unfair?
--------------------------------------------------------------------------------

It is actually the FAIREST option available, and the imbalance is in the raw data,
not in our choice.

Eligible merged Python PRs per agent, AFTER the star and licence filters:

    OpenAI Codex     6,017
    Devin           ~2,000
    Cursor          ~1,100
    Copilot           ~500
    Claude Code          42     <-- this is the entire population

Claude Code only has 42 that pass every filter; 37 survive to the final gold set.
That is a property of the dataset — Claude Code is simply newer and has fewer
merged PRs in public repositories.

Three options existed:

  (a) Use everything.
      -> Codex becomes ~95% of the sample. You are no longer comparing agents,
         you are describing Codex.

  (b) Cap everyone at 37 (the smallest agent).
      -> You throw away ~90% of the usable data. Every agent's estimate becomes
         noisy, and you learn less about all five.

  (c) Cap the big agents at 150, keep everything from the small ones.   <-- CHOSEN

WHY UNEQUAL n DOES NOT MAKE THE COMPARISON UNFAIR:

Every result is a RATE computed within each agent separately. Claude Code's rate
is (its flagged items / its 37 PRs). Codex's rate is (its flagged / its 150).
Nobody is compared on absolute totals, so having more PRs cannot make an agent
look better or worse.

WHAT UNEQUAL n DOES DO:

It makes the small-agent estimates less CERTAIN. A rate over 37 PRs has wider
error bars than a rate over 150. That is a real limitation, and it is exactly why
the reports print COUNTS beside every rate (see Q16) — so you can see when a
number rests on 2 events instead of 50.

FOOTNOTE WORTH KNOWING: TypeScript fixes this problem. There, four of the five
agents reach the 150 cap (Copilot, Cursor, Devin, Codex all at 150; Claude Code
82). TypeScript is the best-balanced corpus in the whole dataset, which is one of
the reasons it was chosen as the second language.


--------------------------------------------------------------------------------
Q3. Why cap at 150? Isn't that a small amount for research?
--------------------------------------------------------------------------------

150 is the per-agent cap, not the corpus size. The totals are:

    Python:       546 PRs across 147 repositories  ->  ~7,600 class/file rows
    TypeScript:   682 PRs across 225 repositories  ->  1,213 classes
    COMBINED:   1,228 real merged pull requests

For context, most published Mining-Software-Repositories papers on code smells
analyse anywhere from a few dozen to a few hundred projects. 372 distinct
repositories is a normal-to-large empirical software-engineering corpus.

Three reasons the cap is 150 specifically:

  1. IT IS NOT THE BINDING CONSTRAINT. Raising the cap to 500 would not help —
     Claude Code only HAS 42 eligible PRs in existence. A higher cap widens the
     imbalance rather than closing it. The cap exists to stop Codex dominating,
     and 150 already achieves that.

  2. THE REAL COST IS LABELLING, NOT SAMPLING. Analysis is cheap and automated.
     But every validation row has to be READ — the source code opened and judged
     one item at a time. That is the expensive, human-paced step, and it does not
     scale with corpus size.

  3. DIMINISHING RETURNS ON CERTAINTY. Going from 37 to 150 PRs sharply narrows
     an agent's error bars. Going from 150 to 500 narrows them much less, while
     tripling clone storage and run time.

The honest limitation to state in the thesis is NOT "the corpus is small" — it is
"the per-agent signal outside SRP is only a handful of pull requests" (see Q16),
which is a property of how rare these smells are per-PR, not of the sample size.


--------------------------------------------------------------------------------
Q5. Those repos that were lost or deleted — why not backfill with new ones until
    the corpus is perfectly balanced?
--------------------------------------------------------------------------------

Short answer: because backfilling would silently BIAS the results, and the loss
is small and now fully documented.

THE LOSS. 18 Python PRs (3.3%) could not be extracted. Each was traced by hand:

    Metta-AI/metta          7 PRs   repository deleted from GitHub
    dai-motoki/haconiwa     1 PR    repository deleted from GitHub
    appdotbuild/agent      10 PRs   repo exists, but history was rewritten
                                    (git reports "not our ref" — commits gone)

TypeScript lost 26 PRs the same way.

WHY WE DID NOT BACKFILL — three reasons:

  1. IT BREAKS STICKY SAMPLING. The gold set is "sticky": once a PR is sampled it
     is kept across re-curations, so cached clones and existing labels stay valid.
     If you replace losses with new draws every time you re-run, the corpus
     changes shape underneath results you have already reported, and no two runs
     are comparable.

  2. IT IS A BIASED REPLACEMENT. The PRs that survive are, by definition, the ones
     in repositories that are still alive and have not rewritten history. Topping
     up from the survivor pool means over-sampling long-lived, stable projects.
     That is survivorship bias introduced deliberately.

  3. IT WOULD NOT HELP THE BALANCE ANYWAY. The imbalance is caused by Claude Code
     having only 42 eligible PRs in the entire dataset — not by the 18 lost ones.
     No amount of backfilling creates Claude Code PRs that do not exist.

WHAT WE DID INSTEAD. Reported it as a REPRODUCIBILITY BOUND, which is a genuine
scientific contribution in its own right:

    "A benchmark defined over specific pull requests DECAYS. Repositories get
     deleted, histories get rewritten, and a replication attempt years later will
     not recover the same corpus."

That sentence is now in the thesis (Chapter 4). It is more valuable than silently
patching the hole would have been. The commit-SHA fallback we built to recover
losses is kept — it costs nothing and recovers PRs wherever the commits still
exist (it recovered 3 in TypeScript, 0 in Python).


================================================================================
PART 2 — THE BEFORE/AFTER METHOD
(your question 4, and your final question 17 — these are the same issue)
================================================================================

This is the most important design decision in the project, so here it is precisely.

TWO DIFFERENT SCOPES ARE USED, DELIBERATELY:

  Principle | Scope     | What is actually measured
  ----------|-----------|-------------------------------------------------------
  SRP       | file/class| The whole files the agent touched, at the AFTER state
  OCP       | PR delta  | Repo rebuilt TWICE; only the difference is charged
  LSP       | PR delta  | same
  ISP       | PR delta  | same
  DIP       | PR delta  | same

HOW THE DELTA WORKS, MECHANICALLY:

  1. Take the PR's merge commit.
  2. Find its FIRST PARENT = the project exactly as it was BEFORE this PR landed.
  3. Rebuild the source tree at both commits (before and after).
  4. Run the SAME detector on both trees.
  5. Subtract:

         smells_after  -  smells_before  =  what THIS pull request introduced

So to answer your question directly: we do NOT benchmark both states and report
both. We compute both, and report ONLY THE DIFFERENCE.

WHY. Attribution. If an agent adds one file to a messy 500-file repository, the
mess is not its fault. Without the delta you would be measuring which repositories
an agent happens to work in, not the quality of what it wrote. Example: if a repo
already contains 40 bad overrides and the PR adds none, the agent scores ZERO for
LSP on that PR — correctly.

--------------------------------------------------------------------------------
YOUR QUESTION 17 IS A SHARP CATCH, AND THERE IS A REAL CAVEAT
--------------------------------------------------------------------------------

You asked: "isn't it benchmarking the whole repo, but only the change because of
that delta thing?"

For the four delta principles: no, only the change is charged. Correct as designed.

BUT FOR SRP: you are right to be suspicious. SRP is NOT a delta. It scores the
WHOLE touched file at the after state. So if an agent adds one small method to a
pre-existing 900-line god class, THAT WHOLE CLASS IS CHARGED TO THE AGENT.

That is a genuine limitation. Why it was accepted:

  * SRP is a property of a class as it stands. "The class became 3 lines more of
    a god class" is not a meaningful measurement — god-classness is not additive.
  * It is why SRP is the ONLY principle with a dense per-class signal; the delta
    principles produce almost nothing per PR.
  * The mitigation is that the whole-repo picture is reported SEPARATELY, as
    context, never as an agent's score:

        "head-state inventory" = 888 dispatch chains, 2,239 override pairs,
                                 348 interfaces, 101 violating overrides

    These describe the CODEBASES the agents worked in. They are never attributed
    to an agent.

This caveat is stated in the thesis threats-to-validity section. It should be
stated out loud in a defence too — it is the kind of thing a good examiner asks,
and having the answer ready is worth more than hoping nobody notices.

PART 3 — THE DETECTORS, IN PLAIN WORDS
================================================================================

--------------------------------------------------------------------------------
Q6. What is a "rubric", and what are the 7 metrics? (SRP)
--------------------------------------------------------------------------------

A RUBRIC is a scoring sheet: a fixed list of thresholds, where you simply count
how many are crossed. It is deliberately transparent — anyone can re-check it by
hand, and there is no hidden model.

A class is flagged (srp_risk) when AT LEAST 2 of these 7 are exceeded:

  METRIC          BAR    WHAT IT MEANS
  --------------- ------ ------------------------------------------------------
  class_loc        200   source lines in the class
  class_wmc         47   Weighted Methods per Class = the sum of every method's
                         cyclomatic complexity. A size-times-complexity measure.
  class_methods     20   number of methods
  class_lcom       0.8   Lack of Cohesion of Methods (explained below)
  file_loc         400   lines in the whole file (file-level rows only)
  func_ccn          15   cyclomatic complexity of the most complex method
                         (roughly: how many branches/decision points it has)
  func_params        6   parameter count of the widest method

A stricter variant (srp_risk_strict) requires >= 3 hits and is reported alongside,
so the results survive an argument about where exactly the bar should sit.

LCOM4 EXPLAINED — this is the interesting one:

  Take all methods of a class. Draw a link between two methods if they either
  share an instance attribute, or one calls the other. Now count how many
  disconnected GROUPS you end up with.

      LCOM = (groups - 1) / (methods - 1)

      0  = one connected blob. Every method is tied to the others. COHESIVE.
      1  = every method is an island. The class is a bag of unrelated functions.

  A god class scores near 1 because its database methods, its email methods and
  its rendering methods touch completely different attributes.


--------------------------------------------------------------------------------
Q7. What is the C3 cohesion suppressor?
--------------------------------------------------------------------------------

C3 = "Conceptual Cohesion of Classes" (Marcus & Poshyvanyk, IEEE TSE 2008). It is
the SEMANTIC counterpart to the structural metrics above.

HOW IT IS COMPUTED (fully deterministic, no AI involved):

  1. For each method, collect its identifiers and docstring words into a bag.
       sendEmail  ->  {send, email, smtp, message, recipient, ...}
       queryRows  ->  {query, rows, sql, connection, cursor, ...}
  2. TF-IDF weight those bags (down-weight words common to every method).
  3. Compute the average pairwise cosine similarity between all method bags.

  HIGH C3  =  all methods talk about the same topic  =  conceptually cohesive
  LOW  C3  =  the methods discuss unrelated subjects

THE SUPPRESSOR RULE:

  If the 7-metric rubric flags a class, BUT its C3 >= 0.4, we UN-FLAG it.

WHY. This kills the single most common false positive: the big, well-written
class. A 400-line class whose every method says "packet, socket, port, bind,
timeout" is a large NETWORKING class — not a god class. Size metrics physically
cannot see the difference. Vocabulary can.

Real measured example from our fixtures:
    god class      C3 = 0.071   (database + email + rendering words mixed)
    cohesive class C3 = 0.337   (geometry words only)


--------------------------------------------------------------------------------
Q8. What is a "PR delta"?
--------------------------------------------------------------------------------

Exactly the before-minus-after subtraction described in Part 2. The term just
means "the change this pull request caused", as opposed to the state of the repo.


--------------------------------------------------------------------------------
Q9. What is a "dispatch chain"? (OCP)
--------------------------------------------------------------------------------

A "switch on type or tag" — Robert Martin's canonical Open/Closed violation:

    if   isinstance(animal, Dog):   return "woof"
    elif isinstance(animal, Cat):   return "meow"
    elif isinstance(animal, Bird):  return "tweet"
    # to add Fish you must EDIT this function
    # => the code is OPEN for modification, CLOSED for extension. Backwards.

The principle says you should be able to add a Fish by ADDING a class, without
editing existing code. A dispatch chain forces the opposite.

Five kinds are detected in Python:
    isinstance chain, type(x) == comparison, match-on-type,
    value switch (if/elif on a string tag), match-on-value

In TypeScript, four kinds:
    switch (x.type)   <- the dominant TS idiom, discriminated unions
    if/else-if tag ladder
    instanceof chain
    typeof chain


--------------------------------------------------------------------------------
Q10. What is "width + closed-set suppressor"? (OCP)
--------------------------------------------------------------------------------

WIDTH = the number of branches in the chain. Thresholds:

    type-based chains:   >= 3 branches   (Python and TypeScript — this is also
                                          Martin's own minimum for a "switch")
    value-based chains:  >= 6 (Python), >= 8 (TypeScript)

The TypeScript tag bar is HIGHER because TS leans heavily on wide discriminated-
union switches; copying Python's 6 would have flagged the median idiom. Both bars
were set from the actual measured distribution (~p90) BEFORE any labelling — this
is what makes the threshold choice non-circular.

CLOSED-SET SUPPRESSOR — the important refinement:

A switch is only an OCP violation if the family it tests is OPEN, meaning new
variants will keep arriving. Some families are CLOSED BY CONSTRUCTION and can
never grow:

  * Python:     a chain over int / str / list / dict / tuple — the builtin types
                are fixed by the language. Also a chain over `ast.*` node types:
                one fixed stdlib grammar.
  * TypeScript: a `typeof` ladder ranges over JavaScript's EIGHT language-fixed
                results (string, number, bigint, boolean, symbol, undefined,
                object, function). It is exhaustive by definition.

Those are exhaustive, so they are not flagged. Effect: Python OCP holdout
precision went 0.33 -> 0.44 with recall unchanged. Every suppressed item was
verified to be a false positive.


--------------------------------------------------------------------------------
Q11. What is "override compatibility + FP suppressor"? (LSP)
--------------------------------------------------------------------------------

Liskov Substitution: if `Child` extends `Parent`, then anywhere the code expects a
`Parent` you must be able to hand it a `Child` and have everything still work.

We check every subclass method against the method it overrides, looking for five
signals in three families:

  STATIC (this replicates mypy's [override] rule, implemented on the AST):
    1. param_required_added  — child demands an argument the parent made optional
    2. param_removed         — child accepts fewer arguments than the parent

  SEMANTIC (variance, checked over the in-repo class hierarchy):
    3. param_type_narrowed   — parent accepts (str | None), child accepts only str
                               => a caller passing None breaks
    4. return_type_widened   — child may return things the parent promised it
                               would not

  BEHAVIOURAL:
    5. refused_bequest       — parent has a WORKING method; child overrides it
                               with nothing but `raise NotImplementedError`.
                               A real example we found:
                                   throw new Error('Not applicable in multisig')

WHY NOT JUST RUN MYPY? Because mypy needs a working, installed environment per
project, and we analyse 147 arbitrary repositories from bare extracted trees.
Our AST rule is the scalable stand-in for a type checker.

FP SUPPRESSOR = four idioms that trip the rule but are not violations:
    (1) the parent is a bare `*args, **kwargs` placeholder (the plugin pattern —
        it declares no real contract)
    (2) variance measured against `Any` or an unbound TypeVar (meaningless)
    (3) optional parameters dropped but absorbed by a `**kwargs`
    (4) factory classmethods (`create`, `from_dict`) — constructor-like, not
        substitutable call sites

Effect: Python LSP holdout precision 0.42 -> 1.00, recall kept at 1.00. That
turned LSP from a screen into the project's most precise detector.

IMPORTANT TYPESCRIPT DIFFERENCE (a headline finding): TypeScript methods are
BIVARIANT by design. We probed the real compiler (tsc 5.9.3, strict mode): dropping
a trailing parameter, narrowing a parameter, and making an optional parameter
required all produce ZERO errors. And JavaScript ignores extra arguments at
runtime. So `param_removed` is safe at BOTH levels in TypeScript and is NOT
counted there — whereas in Python the same edit raises TypeError at the call site.
It had fired on 15 of 23 pairs, so keeping it would have invented the entire
TypeScript LSP result.


--------------------------------------------------------------------------------
Q12. What is "abc/Protocol width + implementer stub ratio"? (ISP)
--------------------------------------------------------------------------------

Interface Segregation: no client should be forced to depend on methods it does not
use. Fat interfaces force exactly that.

WHAT COUNTS AS AN INTERFACE IN PYTHON:
    * a class inheriting from `abc.ABC` (explicit abstract base class)
    * a `typing.Protocol` (structural typing)
    * "implicit" — a stub-heavy base class that has at least one real subclass

WIDTH = how many methods the interface demands.

STUB RATIO = of the methods a class actually implements, what fraction are FAKE:
    empty body / `pass` / `return None` / bare `raise NotImplementedError`

THE KEY POINT: WIDTH ALONE IS NOT A VIOLATION.

A 15-method interface that every implementer fully implements is a cohesive
service, not a design fault. The flag requires WIDTH **AND** FORCED STUBS —
evidence that somebody implementing it is faking methods they do not need. That
is literally what the principle forbids.

Our clearest true positive: `TestingLanguageService` implements a 6-method
interface, genuinely needs ONE of them, and writes
`throw new Error('Method not implemented.')` for the other five.

TYPESCRIPT NEEDED TWO EXTRA SCOPE CUTS (this was the noisiest part of the port):
    1. 82.6% of TypeScript `interface` declarations have ZERO behavioural members
       — in TS, `interface` is mostly how you write a plain data shape
       (`interface User { name: string }`). Those cannot force anyone to
       implement anything.
    2. Of the ones that DO declare behaviour, 87.7% have no implementer at all —
       they are React `Props` bags, context values, store shapes. Nobody
       `implements` them; consumers just destructure them.

    Inventory: 3,733 declared -> 648 behavioural -> 109 real contracts.

    Before these cuts, the tool reported "Claude Code violates ISP in 11.5% of its
    TypeScript PRs". After: 3 PRs of 78. The original figure was an artefact.


--------------------------------------------------------------------------------
Q13. What are "graph, Tarjan cycles, Martin A/I/D"? (DIP)
--------------------------------------------------------------------------------

Dependency Inversion: high-level modules should not depend on low-level details;
both should depend on abstractions.

IMPORT GRAPH
    Nodes = modules. Edges = "module A imports module B". Built from the source,
    resolving relative imports, path aliases, and (in TypeScript) a monorepo's own
    workspace packages.

TARJAN'S ALGORITHM -> CYCLES
    Tarjan's algorithm finds "strongly connected components" — groups of nodes
    where you can follow the arrows from any member back to itself. A component
    with more than one module IS A CIRCULAR DEPENDENCY:

        a.py imports b.py, and b.py imports a.py

    Cycles are the strongest DIP smell: neither module can be understood, tested
    or reused without the other. This turned out to be the ONLY trustworthy part
    of our DIP detector — precision 1.00 (5 flags, 5 real) in TypeScript.

MARTIN'S METRICS (Robert Martin, "Agile Software Development"), per package:

    I = Instability  = outgoing / (incoming + outgoing) dependencies
        0 = nothing depends outward from you; you are stable/hard to change
        1 = you depend on everything; you are unstable/easy to change

    A = Abstractness = abstract classes / total classes
        0 = fully concrete;  1 = fully abstract

    D = Distance     = |A + I - 1|
        The "main sequence" is the ideal line A + I = 1: stable packages should be
        abstract, unstable ones should be concrete. D measures how far off that
        line a package sits. High D = either a rigid concrete core everyone
        depends on, or a useless abstract package nobody uses.

    WE MEASURED D AND IT DOES NOT WORK. Labelling showed 0 of 10 `mean_d_worse`
    flags were real violations, and four of those ten had added NO new dependency
    at all — the number moved purely because adding modules recomposes the graph.
    Python's earlier validation had suspected the same thing. Two independent
    languages, same verdict: D is noise, cycles carry the whole signal. That is
    a negative result we report, not hide.

THE MOST ACTIONABLE FINDING IN THE WHOLE BENCHMARK came out of the cycle half —
the BARREL-IMPORT CYCLE. All five real TypeScript cycles have the same shape: the
agent adds a new small module, and that module imports its package's root
`index` file, which in turn re-exports the new module. Circle closed.
ALL FIVE AGENTS did it, exactly once each. A human reviewer would say "import the
specific file, not the barrel."

--------------------------------------------------------------------------------
Q14. What are "holdout" and "seed"?
--------------------------------------------------------------------------------

SEED. The fixed number (42) that makes "random" sampling reproducible. Same seed,
same rows selected, forever, on any machine. Without it, no one — including you —
could ever regenerate the exact sample you reported on.

HOLDOUT. Use the school-exam analogy:

    TUNING SAMPLE  =  practice questions.
                      You look at them. You see where your ruler was wrong.
                      You adjust the ruler.

    HOLDOUT        =  the real exam.
                      Fresh rows, drawn with a different seed (42 + 1000),
                      with all tuning rows explicitly excluded.
                      You look at it ONCE.

ONLY THE HOLDOUT SCORE COUNTS. The tuning score is contaminated by definition:
you shaped the ruler around those exact examples, so of course it does well on
them.

BURNED HOLDOUT. Once you have looked at a holdout in order to IMPROVE the ruler,
it stops being a fresh exam — it has become practice. You now need a brand-new
third sample. Ours for SRP and OCP are burned; any future change to those rubrics
requires drawing a fresh sample.


--------------------------------------------------------------------------------
Q15. What does "Agreement, tuning -> holdout" mean?
--------------------------------------------------------------------------------

It is the drop between the two numbers — and that drop is the size of your own
self-deception. Our project contains the textbook illustration of it:

    SRP tuning precision   0.82     "excellent!"
    SRP holdout precision  0.33     the truth

    WITHOUT THE HOLDOUT WE WOULD HAVE PUBLISHED A NUMBER 2.5x TOO GOOD.

"Agreement" specifically means agreement between our deterministic rubric and the
reading judge — NOT agreement with human ground truth. Every label in this project
was produced by an LLM (Claude) reading the actual source code. That is why the
CSV column is named `llm_srp_risk` rather than `srp_risk_true`, and why the thesis
always says "rubric-versus-LLM-judge agreement". Human expert labels remain the
top outstanding rigour item.

CURRENT SCORES (precision / recall):

    HOLDOUT (trustworthy):
      LSP  Python      1.00 / 1.00    high-precision detector
      ISP  Python      1.00 / 1.00    crisp, but few distinct positives
      OCP  TypeScript  0.80 / 0.80    best delta detector
      OCP  Python      0.44 / 0.80    useful screen
      SRP  Python      0.33 / 1.00    high-recall screen
      SRP  TypeScript  0.21 / 1.00    same character, weaker

    TUNING STAGE ONLY (may be optimistic — no holdout drawn yet):
      LSP  TypeScript  0.73 / 0.89
      DIP  TypeScript  1.00 on cycles / 0.00 on distance
      ISP  TypeScript  0.17 / 1.00
      DIP  Python      0.22 / 0.67    single small sample

WHAT "PRECISION" AND "RECALL" MEAN HERE:
    Precision = of the things we flagged, how many were real?     (few false alarms)
    Recall    = of the real problems, how many did we catch?      (few misses)

A high-recall / low-precision tool is a SCREEN: it misses nothing, so use it to
build a shortlist, then read the shortlist. A high-precision tool is a DETECTOR:
you can trust its flags directly.


--------------------------------------------------------------------------------
Q16. "Pooled AND macro-per-repo rates, with counts" — how, and why?
--------------------------------------------------------------------------------

TWO WAYS TO AVERAGE:

    POOLED  =  all flagged items  /  all items
               (throw every class from every repo into one pile)

    MACRO   =  compute the rate INSIDE each repository first,
               then average those per-repo rates
               (each repository gets exactly one vote)

WHY BOTH — AND WHY THEY DISAGREE:

    52% of OpenAI Codex's Python classes come from ONE SINGLE REPOSITORY
    (MontrealAI). Pooled, that one repo's character IS Codex's score. Macro gives
    it one vote among 24 repositories.

    The rankings literally REVERSE:
        Codex pooled  =  BEST
        Codex macro   =  WORST

MACRO IS THE FAIR NUMBER, so every report leads with it. Beside it we print
`top_repo_share` — the fraction of an agent's data coming from its single largest
repo — so the reader can see the concentration for themselves.

"WITH COUNTS" MEANS WRITING THIS:

        Cursor  5 of 70          not:   Cursor 7.1%

WHY THIS MATTERS ENORMOUSLY:

    The ENTIRE Python OCP signal is ELEVEN flagged pull requests across all five
    agents:

        Cursor        5 of  70
        Devin         3 of 112
        Claude Code   2 of  34
        Copilot       1 of  85
        OpenAI Codex  0 of 150

    Python ISP is 2 PRs. Python LSP is 1 PR.

    On numbers that small, ONE pull request moves an agent by several percentage
    points. A percentage hides that fragility completely; a count cannot.

    This is why the defensible claim is:
        "OCP produces a measurable per-PR signal where the inter-unit principles
         produce essentially none"
    and NOT a leaderboard of which agent is best at OCP.

    It is also why three previously-reported conclusions had to be withdrawn or
    weakened during the audit — they were built on counts this small.


================================================================================
ONE-PAGE SUMMARY — THE FIVE THINGS WORTH REMEMBERING
================================================================================

1. THE DELTA IS THE ATTRIBUTION ARGUMENT. Four of five principles rebuild the repo
   before and after and charge only the difference. SRP is the exception and
   scores the whole touched file — a limitation to state openly.

2. MACRO BEATS POOLED, AND COUNTS BEAT RATES. One repo can be half an agent's
   data, and the whole OCP signal is 11 pull requests.

3. THE HOLDOUT IS NON-NEGOTIABLE. Our own SRP number fell from 0.82 to 0.33 when
   tested honestly. Every "success" claim in this project survived that test, or
   is explicitly marked as tuning-stage.

4. STRUCTURE BOUNDS RECALL; PRECISION IS ONLY RECOVERABLE FOR NAMEABLE IDIOMS.
   Where false positives form a finite, describable family (LSP's four idioms,
   OCP's closed sets), a deterministic rule fixes them. Where they are genuinely
   semantic (SRP's large-but-cohesive classes), nothing worked — not embeddings,
   not a trained classifier.

5. PORTING TO A NEW LANGUAGE IS NOT SWAPPING THE PARSER. The same edit is a
   violation in Python and idiomatic in TypeScript. Thresholds, one principle's
   signal set, and another's whole notion of a "contract" all had to be
   re-derived from the target language's semantics.
