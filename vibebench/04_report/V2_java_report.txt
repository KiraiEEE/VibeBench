============================================================================
V2 RULES -- READ BEFORE QUOTING ANY OUTCOME NUMBER
============================================================================
  * A BALANCED CORPUS IS NOT A REPRESENTATIVE ONE. The drawn corpus is
    roughly 1:1 merged to not-merged; the real population is 80.9% merged.
    Every PER-OUTCOME rate above is valid exactly as printed. Any figure
    POOLED ACROSS outcomes is a balanced-design figure and is wrong for
    the world unless it is reweighted to {'merged': 0.809, 'rejected': 0.095, 'open': 0.096}.
    Say which one every headline number is. That is one sentence in the
    methods section and it removes an easy attack.
  * `REJECTED` IS NOT `REFUSED ON QUALITY`. Measured on the eligible pool,
    a rejected PR is HALF as likely to carry any recorded review as a
    merged one. Only the `changes_requested` stratum carries an explicit
    maintainer objection, and it is small -- print its COUNT beside every
    rate computed on it. Never publish a bare merged-vs-rejected rate as
    if rejection meant refusal.
  * PREFER THE WITHIN-REPO PAIRED CONTRAST when it disagrees with the
    pooled one. The pooled contrast mixes a repository effect into the
    outcome effect because the two sides are not drawn from the same
    projects; the paired one removes it.
  * CHECK THE SIZE AND AGE BLOCKS before reading an outcome difference as
    a conformance difference. A bigger PR has more chances to violate,
    mechanically, and an older PR sits in a different codebase.
  * PRECISION MUST BE EVEN ACROSS OUTCOMES. score_labels.py prints it per
    outcome; a spread above 15 points means the contrast is partly a
    detector artefact and is not a statement about code.
  * THE JUDGE NEVER SEES THE OUTCOME. make_java_census.py withholds it
    into a sidecar and check_label_file.py FAILS if it leaks. A judge who
    can see `rejected` can produce this result out of nothing.
