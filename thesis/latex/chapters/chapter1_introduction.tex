\section{Research Context}
\label{sec:research-context}

AI tools for software development have changed in what they do. GitHub Copilot (2021) and Amazon
CodeWhisperer (2022) completed the next line or block, and the developer decided what to keep.
Newer tools work at the level of a whole task. Claude Code (Anthropic, 2025), Cursor's agent mode,
Devin (Cognition, 2024), OpenAI Codex CLI (2025), Google Jules (2025) and open-source tools such as
OpenCode and Aider read an issue, plan steps, edit files, run tests and revise their changes without
a human approving each step. This loop, in which a language model alternates reasoning with tool
calls, was described as the ReAct pattern \citep{yao2023react}.

agents (below) take a task and return a finished change. The first half of 2025 is enlarged: the

\label{fig:timeline}
\end{figure}

A developer can now hand an agent a feature description and receive a pull request. The informal
term \emph{vibe coding} describes this way of working: the developer states the intent and the agent
writes the implementation. \citet{konrad2026vibe} describe a related effect, \emph{vibe
architecting}, in which structural decisions follow from how a prompt is worded. In one of their
examples the same chatbot task, given three different prompts, produced systems of 141 lines in two
files and of 827 lines in six files, with no architecture decision records and no recorded
rationale.

These agents already contribute to real projects. The AIDev dataset \citep{li2025aidev} collects
pull requests opened by autonomous coding agents on public GitHub repositories, and studies built
on it work with thousands of such requests. \citet{cynthia2026agents}, for example, analyse 9,427
agent pull requests and find that core and peripheral developers use agents for different tasks and
follow different merge practices. Because agent-written code is reviewed and merged into real
software, its structural quality can be studied on real data. This thesis uses the same dataset.

Uptake and merge figures describe use, which is only one part of software quality. Software
engineering has a longer vocabulary for design: Brooks's analysis of accidental complexity
\citep{brooks1975mythical}, Martin's design principles \citep{martin2000solid}, later grouped under
the acronym SOLID, and the code smells catalogued by \citet{fowler1999refactoring}. Code can pass
its tests and still be tightly coupled and expensive to change, and most of the cost of software is
spent on maintenance after the first release.

Recent studies suggest that AI assistance affects this side of quality. \citet{xu2025productivity}
report that after Copilot was introduced, core developers reviewed 6.5\% more code and their own
original code output fell by 19\%. \citet{zhu2026smells} describe a \emph{Volume-Quality Inverse
Law}: in AI-generated repositories, code volume is a near-perfect predictor of structural
degradation, and neither functional correctness nor detailed prompting prevents it. This thesis
asks whether similar problems appear in the code that three widely used agents submit to real
projects.

\section{Problem Statement}
\label{sec:problem-statement}

Coding agents are mostly evaluated on properties that are easy to test automatically, and less on
the properties that decide how expensive code will be to maintain.

\paragraph{Benchmarks.} HumanEval \citep{chen2021codex}, MBPP, BigCodeBench
\citep{zhuo2024bigcodebench} and SWE-bench \citep{jimenez2024swebench} all ask whether generated
code passes a set of tests, usually for one function or one issue. Pass@$k$ is well defined and
reproducible, but it says nothing about whether the surrounding code is well structured or whether
a maintainer would accept the change. ProjDevBench \citep{lu2026projdevbench} evaluates end-to-end
project development and finds that agents struggle with system design, time complexity and resource
management, but it contains 20 problems.

The distance between benchmark scores and acceptance by maintainers has been measured.
\citet{metr2026sweverified} asked maintainers to review agent patches that pass SWE-bench Verified:
roughly half would not be merged, maintainer merge decisions were on average about 24 percentage
points below the automated score, and maintainers merged only 68\% of the human reference patches.
SlopCodeBench \citep{slopcodebench2026} gives agents tasks that are extended over many checkpoints
and finds that structural erosion increases in 77\% of trajectories, which a single pass@$k$ score
cannot show.

\paragraph{Structural quality.} When language models are prompted to detect SOLID violations,
Single Responsibility violations are found most easily and Dependency Inversion violations least
easily, and accuracy falls as code becomes more complex \citep{pehlivan2025solid}. Large projects
generated with an AI IDE pass most functional checks yet contain design issues such as large methods
and duplicated code \citep{beyond2026designissues}. \citet{zhu2026smells} describe a ``machine
signature'' of defects in agent-written code: broken abstractions, duplication, over-engineering and
verbosity. None of these studies compares several agents on the same corpus of real contributions.

The NITR benchmark \citep{zhu2026nitr} shows how hard some structural tasks are for current agents:
they succeed on 4.3\% of dependency-control tasks and on 15.2\% of responsibility-decomposition
tasks, and 13.3\% of outcomes pass every functional test while failing the structural check.

\paragraph{Models and agents.} Most evaluations vary the language model and keep the agent software
fixed. \citet{bensghaier2026harness} test that assumption. They study five open-source agent
harnesses and then hold the model fixed while evaluating 35 consecutive releases of Qwen Code CLI on
50 SWE-bench Verified tasks. Quality changes between releases, and they trace the changes to
specific pull requests in the harness. The agent software therefore has an effect of its own, and
someone choosing a tool chooses an agent, not only a model. This thesis compares three agents:
Claude Code, GitHub Copilot and OpenAI Codex.

In short, current evaluation practice says little about the design quality of the code agents
contribute to real repositories. Adoption decisions may therefore rest on functional scores alone,
while maintenance costs accumulate elsewhere.

\section{Research Objectives}
\label{sec:research-objectives}

The main question is whether code written by coding agents follows established object-oriented
design principles, in addition to working.

One scoping decision bounds every later claim. The five SOLID principles describe classes and the
relations between them: a class, a dispatch chain, an override, an interface and its implementers,
a dependency between modules. All five measurements in this thesis therefore work below the level
of the package. When the thesis uses the word architecture, it means design structure at this
level, not the decomposition of a system into components and layers. The only package-level
instrument, the abstractness and instability plane of Section~\ref{sec:zones-detail}, describes
packages and raises no flags.

The objectives are:

\begin{enumerate}[label=\textbf{O\arabic*.}, leftmargin=1.6cm]
  \item Build a reproducible framework that measures adherence to the five SOLID principles (Single
  Responsibility, Open/Closed, Liskov Substitution, Interface Segregation and Dependency Inversion)
  on real pull requests written by coding agents, using one deterministic structural detector per
  principle.
  \item Build the corpus from all three outcomes a pull request can have: merged, rejected and still
  open. A corpus of merged requests shows what maintainers accepted, which is not the same as what
  agents produced.
  \item Measure how well each detector agrees with an independent reading of the code. A judge reads
  the source of a stratified sample of flagged and unflagged entities, and precision and recall are
  reported for each principle. The judge is a large language model, a technique validated for SOLID
  detection by \citet{pehlivan2025solid}, so every figure is agreement between the detector and the
  judge.
  \item Compare three agents, Claude Code, GitHub Copilot and OpenAI Codex, with rates reported both
  pooled and averaged over repositories.
  \item Determine where design problems are located: inside one unit (a class or a method) that a
  single change can write in full, or in a relation between units (a dependency, an interface, an
  override) that a single change rarely writes on both sides.
  \item Repeat the whole study in Python, with the same agents, curation rules, validation procedure
  and statistical model, to find out which results hold in both languages.
\end{enumerate}

Three practical constraints shaped the design. First, generating many new repositories with each
agent would require compute and API budgets that were not available. The study therefore measures
code the agents actually submitted to open-source projects, taken from the AIDev dataset
\citep{li2025aidev}. This is cheaper, it reflects real tasks, and each pull request is a bounded
change made by one agent.

Second, the framework was built first for Java and then applied to Python, and the two languages
play different roles. A common objection to measuring SOLID is that the principles fit poorly in
languages that do not require object orientation. Java answers that objection: classes are
compulsory, \texttt{interface} is a keyword, \texttt{@Override} is explicit and subtyping is
nominal, so each principle has a direct counterpart in the syntax. Python is the opposite case:
classes are optional, contracts are conventions, and no compiler checks an override against its
base. A result found in both languages is unlikely to be a side effect of Java's type system. Only
the fact-extraction layer of the framework depends on the language, so the Python study replaces the
extractor and recalibrates the thresholds and changes nothing else.

Third, the agent set follows from the data. The same three agents are used in both languages so
that every cross-language comparison has the same agents on both sides. Cursor and Devin were
excluded because they have too little Java: 94 eligible Java pull requests for Cursor, 72.3\% of
them from three repositories, and 6 for Devin. Google Jules was excluded because it appears for the
first time in this release of the dataset, so its attribution of pull requests has no earlier
release to be checked against.

\section{Research Questions}
\label{sec:research-questions}

The study answers four research questions. Chapter~\ref{ch:methodology}
(Section~\ref{sec:rqs}) describes how each is answered.

\begin{description}[leftmargin=2.4cm,style=nextline]
  \item[RQ1 (Adherence and differentiation)] Do coding agents differ in their adherence to the five
  SOLID principles on real pull requests, where do the differences lie, and does structural quality
  differ between the requests maintainers merged and those they did not?

  \item[RQ2 (Measurability and construct validity)] Can SOLID adherence be measured at repository
  scale with deterministic structural detectors, how well do the detectors agree with an independent
  reading judge, and how well do they agree with established, independently developed analysers run
  on the same code?

  \item[RQ3 (Locus of risk)] Are design problems mainly located inside single units, which one change
  can write in full, or in relations between units, which one change rarely writes on both sides?

  \item[RQ4 (Generalisation across languages)] Which answers to RQ1 to RQ3 still hold when the same
  framework, agents and procedure are applied to Python, a language without compulsory classes,
  declared contracts or compile-time type checks?
\end{description}
