\section{Research Context}
\label{sec:research-context}

The last few years have seen a marked change in what AI tools for software development actually
do. Early systems like GitHub Copilot (2021) and Amazon CodeWhisperer (2022) were, in essence,
smart autocomplete, they suggested the next line or the next few lines, and the developer
decided what to keep. More recent tools work differently. Claude Code (Anthropic, 2025), Cursor's
agent mode, Devin (Cognition, 2024), OpenAI Codex CLI (2025), Google Jules (2025) and open-source
entrants such as OpenCode and Aider are designed to operate at the level of entire tasks: they read a requirement or an issue description, plan a sequence of steps,
write code, run tests, interpret failures, and revise, all without a human in the loop for each
individual decision. The underlying pattern here is the ReAct paradigm (Reasoning and Acting),
which interleaves natural-language reasoning with tool invocations to handle multi-step problems
autonomously.

In practice, this means a developer can hand off a feature description and receive a working
implementation. The term \emph{vibe coding} has emerged somewhat informally to describe this mode
of collaboration, the developer maintains intent and direction, while the agent handles the
implementation. A related and perhaps more concerning pattern is what \citet{konrad2026vibe} call
\emph{vibe architecting}: structural decisions shaped implicitly by how a prompt happens to be
worded, rather than by deliberate design. Their study shows the same task with different prompts
can produce systems ranging from 141 lines across two files to 827 lines across six, with no
architectural decision records and no recorded rationale. That kind of structural variability is
one of the things this thesis tries to characterise more precisely.

Uptake is no longer speculative, and it can be observed directly rather than through vendor
surveys. The AIDev dataset \citep{li2025aidev} catalogues pull requests opened by autonomous
coding agents against public repositories, and studies built on it already work at the scale of
thousands: \citet{cynthia2026agents} analyse 9,427 agent-generated pull requests, and find that
agent use, review effort, and merge rates all differ systematically between core and peripheral
contributors. Agent-authored code is being reviewed and merged into real projects today. That is
what turns its structural quality from a forecast into an empirical question, and it is the
same dataset this thesis draws its corpus from.

What these figures measure, though, is speed, one narrow slice of what software quality means.
The engineering discipline has spent decades developing a richer vocabulary: Frederick Brooks'
analysis of accidental complexity in \emph{The Mythical Man-Month} \citep{brooks1975mythical},
Robert C. Martin's SOLID principles \citep{martin2000solid}, and Fowler et al.'s taxonomy of code
smells in \emph{Refactoring} \citep{fowler1999refactoring}. The underlying point across all of this
work is that passing tests and being well-designed are different things. A codebase can be
functionally correct while also being tightly coupled, poorly factored, and expensive to change,
and most of the cost of software comes during maintenance, not initial development.

There is growing evidence that AI-generated code raises exactly these concerns. \citet{xu2025productivity}
find that after Copilot adoption, core developers in their study showed a 19\% drop in original
code productivity alongside a 6.5\% increase in review burden, a measurable trade-off that
productivity figures alone would obscure. A separate study by \citet{zhu2026smells} documents what
they term a \emph{Volume-Quality Inverse Law}: in AI-generated repositories, code volume predicts
structural degradation almost perfectly, and neither functional test coverage nor prompt detail
appears to mitigate this. That is a striking finding, if it generalises. This thesis takes it as
part of its motivation, and examines whether similar patterns hold across a broader set of agents
and tasks.

\section{Problem Statement}
\label{sec:problem-statement}

The evaluation problem is, at its core, a mismatch: the benchmarks used to assess coding agents are
designed around things that are easy to measure automatically, not around the things that actually
matter when code is deployed and maintained.

\paragraph{On benchmark adequacy.} HumanEval, MBPP, BigCodeBench \citep{zhuo2024bigcodebench}, and
SWE-bench \citep{jimenez2024swebench} share a common structure, they ask whether a model
produces code that passes a set of tests, usually at the function or single-issue level. Pass@$k$
and coverage metrics are well-defined and reproducible, but they say nothing about whether the
surrounding system is coherently structured, whether the code will be easy to modify, or whether a
real reviewer would accept it. ProjDevBench \citep{lu2026projdevbench} is one of the few attempts
to evaluate end-to-end project generation, and it exposes genuine difficulties with system design,
complexity optimisation, and resource management, but across only 20 problems, which limits
what can be concluded.

Separate evidence suggests the benchmark--reality gap is larger than assumed. A 2026 analysis by
METR \citep{metr2026sweverified} found that roughly half of solutions passing SWE-bench Verified
would not be merged by the repositories' own maintainers, about a 24-point gap between
benchmark score and real-world acceptance, and roughly twice the rejection rate of the human
reference solutions. A different effort, SlopCodeBench \citep{slopcodebench2026}, finds agent code
quality erodes as tasks are extended across successive checkpoints, a dimension pass@$k$ cannot
capture at all.

\paragraph{On structural quality.} The structural evidence is worth taking seriously. Studies that
prompt LLMs to detect SOLID violations directly \citep{pehlivan2025solid} report that some
principles are found reliably while Dependency Inversion is consistently the hardest, and that
accuracy falls as code grows more complex. Work on large AI-IDE-generated projects
\citep{beyond2026designissues} finds that functionally-working code still carries design issues
such as oversized, multi-responsibility methods. \citet{zhu2026smells} characterise a recurring
``machine signature'' in agent-authored defects, broken abstractions, systematic duplication,
over-engineering, arising from pattern mimicry rather than deadline pressure, which may make it
less visible in review. What these leave open is how such deficiencies manifest at system scale,
and whether individual agents differ once measured on a common corpus, the questions this
thesis takes up.

The NITR benchmark \citep{zhu2026nitr} gives a sense of the depth of the structural problem: AI
agents succeed on dependency-control tasks only 4.3\% of the time and on responsibility-decomposition
tasks only 15.2\% of the time. Perhaps more troublingly, 13.3\% of their AI-generated code passes
all functional tests while failing architectural quality checks, what the authors call
\emph{structural oracle failure}. It suggests that test suites, as currently constructed, are not
detecting something important.

\paragraph{On what is being evaluated.} Most existing work varies the underlying model, GPT-4,
Claude 3.5, Gemini Pro, while holding the agentic workflow constant. That choice assumes the
scaffolding is a neutral wrapper, and the assumption has now been tested directly.
\citet{bensghaier2026harness} hold the language model fixed and vary only the \emph{agent harness},
the middleware orchestrating prompts, tool execution and reasoning loops, across 35 sequential
releases of five open-source harnesses. Evaluating Qwen Code CLI releases against a fixed task set,
they trace quality fluctuations to specific development patterns and architectural components, and
link individual pull requests in the harness to measured shifts in agent performance. The harness
is therefore not a constant to be factored out; it is a moving part with its own measurable effect.
Evaluating agents rather than models is not a terminological preference, it is the relevant unit of
analysis for someone choosing between tools, and the scaffolding, context management and tool-use
protocols specific to a given agent (Copilot, Claude Code and OpenAI Codex, the three studied here)
are part of what is being measured.

Taken together, these gaps point to a concrete problem: current evaluation practices leave
architectural coherence, maintainability, deployability, and iterative refinement capability
largely uncharacterised at repository scale. The risk is that adoption decisions rest on a narrow
and favourable slice of the evidence, while the longer-term costs, inflated maintenance burden,
brittle architecture, deferred refactoring, accumulate unobserved.

\section{Research Objectives}
\label{sec:research-objectives}

The core question motivating this work is whether modern coding agents produce code that not only
functions correctly, but also holds up against the structural and design standards that software
engineering practice has developed over time. That is a harder question than it sounds, and
current evaluation frameworks are not well-equipped to answer it.

More specifically, this thesis:

\begin{enumerate}[label=\textbf{O\arabic*.}, leftmargin=1.6cm]
  \item Constructs a reproducible, repository-scale framework that measures adherence to all five
  \textbf{SOLID} design principles, Single Responsibility, Open/Closed, Liskov Substitution,
  Interface Segregation, and Dependency Inversion, on \textbf{real pull requests written by
  autonomous coding agents}, using \textbf{deterministic structural proxies} computed one principle
  at a time.
  \item Builds that corpus on \textbf{all three outcomes a pull request can have}, merged,
  rejected, and still open, rather than on merged code alone. A merged-only corpus measures
  what maintainers accepted, not what agents produced, and cannot distinguish the two. Including
  the requests that were closed unmerged makes the comparison possible.
  \item Turns construct validity into a measured quantity: each proxy is \textbf{validated against
  an independent reading judge} on a stratified sample of flagged and unflagged entities, reporting
  per-principle precision and recall rather than assuming that a structural metric captures a
  semantic principle. (The judge is a large language model reading the actual source, a technique
  validated for SOLID detection by \citet{pehlivan2025solid}; the resulting figures are
  rubric-versus-judge agreement.)
  \item Applies the framework to \textbf{three leading coding agents}, Claude Code, GitHub
  Copilot, and OpenAI Codex, and characterises per-agent adherence profiles, reported both
  pooled and controlled for repository mix.
  \item Investigates \textbf{where code-quality risk concentrates}: inside a single unit (a class,
  a method) that one change can author whole, or in a relation between units, a dependency
  graph, an interface, an override chain, that a single change rarely authors on both sides.
\end{enumerate}

Three practical constraints are worth being explicit about. First, fully automated, from-scratch
repository generation at scale would require compute and API access beyond what is available for
this project; the study therefore evaluates code the agents \emph{actually submitted} to real
open-source projects, drawn from the AIDev dataset \citep{li2025aidev}, which is both cheaper and
more ecologically valid, and which also makes each pull request a bounded unit attributable to one
agent.

Second, the framework is realised for \textbf{Java}. Java is where the strongest objection to the
whole design, that these principles are an awkward fit for languages that do not mandate object
orientation, can be tested directly, since Java makes classes compulsory, \texttt{interface}
unambiguous, \texttt{@Override} explicit, and subtyping nominal. Every SOLID principle has a
syntactic home in the language, so a structural proxy is measuring the thing the principle is
about rather than a distant proxy for it. The framework is language-parameterised by construction:
the fact-extraction layer is the only language-specific component, and a second language can be
added without changing the pipeline, the validation procedure, or the reporting.

Third, the agent set is determined by data volume rather than preference. The three agents studied
are the only ones in the dataset with enough Java pull requests across all three outcomes to
support a mix-controlled comparison.

\section{Research Questions}
\label{sec:research-questions}

The study is organised around three research questions. They are developed in full, with their
methods of answer, in Chapter~\ref{ch:methodology} (Section~\ref{sec:rqs}).

\begin{description}[leftmargin=2.4cm,style=nextline]
  \item[RQ1 (Adherence and differentiation)] Do modern AI coding agents differ in their adherence
  to the five SOLID principles on real pull requests, where do those differences concentrate, and
  does structural quality differ between the requests maintainers merged and the requests they
  turned down?

  \item[RQ2 (Measurability and construct validity)] Can SOLID adherence be measured at repository
  scale with deterministic, reproducible structural proxies; how faithfully do those proxies agree
  with an independent reading judge; and do they agree with \textbf{established, independently
  developed analysers} run over the same code?

  \item[RQ3 (Locus of risk)] Is code-quality risk primarily intra-unit or inter-unit, that is,
  does it live inside units that a single change authors whole, or in relations between units that
  a single change rarely authors on both sides?
\end{description}
