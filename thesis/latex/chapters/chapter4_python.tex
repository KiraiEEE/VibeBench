\section{Replication in Python (RQ4)}
\label{sec:python}

The Java results could describe the agents or only how the agents write Java. Change size dominates
every principle, one agent difference remains after adjustment, and most design problems in the
touched code were already there. Each of these could depend on a language with compulsory classes,
declared contracts and a compiler that rejects a family of substitutability faults. This section
applies the same framework, agents, curation rules, validation procedure and statistical model to
Python.

Python differs from Java on each of these points. A module need not declare a class; a contract can
be an \texttt{abc.ABC}, a \texttt{typing.Protocol} or a base class whose methods raise
\texttt{NotImplementedError}; nothing checks subtyping; and the faults \texttt{javac} rejects are
legal until the program runs.

\subsection{Corpus}
\label{sec:python-corpus}

The Python corpus comes from the same AIDev release with the same repository filters (at least 25
stars and a licence from the allowlist of Section~\ref{sec:dataset}), keeping pull requests that
change Python files. Two sampling choices differ from Java. The draw is balanced exactly on agent and
outcome, with 1{,}400 merged, 700 rejected and 250 open requests per agent (2{,}350 per agent). It is
also stratified by repository, so no repository contributes more than 0.4\% of any agent and outcome
cell, against 17.2\% for the most concentrated Java cell. The curated corpus contains 7{,}050 pull
requests from 3{,}974 repositories, created between February 2025 and March 2026.

Some of this attrition is source loss, not a scoping decision. 496 Python pull requests (7.0\%) could
not be retrieved: the dataset has no file list for them, they have no merge commit or recorded
commits, and their branch has been deleted from GitHub. The loss is uneven: 5.1\% of merged requests
against 11.0\% of rejected ones, and 14.3\% of Copilot's requests against 3.6\% and 3.1\% for the
other agents. The lost requests were not replaced, because replacements could only come from requests
whose branches still exist, which would tie retrievability to the outcome being compared.

\subsection{Changes to the Instrument}
\label{sec:python-instrument}

Only the fact extractor was replaced. Python source is parsed with the standard library's
\texttt{ast} module, without a JVM or a symbol solver, into the same record of types, members,
supertypes, imports and member accesses that the Java extractor writes. The detector logic, the delta
comparison, the attribution rules, the validation procedure, the report and the joint model are the
same code as for Java. Three things changed.

\textbf{Thresholds were recalibrated before any label existed.} Java percentiles do not transfer:
Python classes are smaller and Python expresses dispatch differently. A calibration pass over all
7{,}050 requests recorded every metric with flags switched off, thresholds were set near the 90th
percentile, and the result files were deleted and the pass run again, so no flag predates its
threshold. Table~\ref{tab:py-thresholds} compares the two sets.

\textbf{The Liskov detector keeps the signals Java does not need.} In Java a changed parameter list
makes an overload and parameter types are invariant, so the Java detector does not look for either
(Section~\ref{sec:findings}, Finding~1). In Python both are real faults. Besides refused bequest and
a widened return type, the Python detector flags a removed parameter, an added required parameter
and a narrowed parameter type.

\textbf{Contracts are recognised by convention.} Python has no \texttt{interface} keyword. The
detector treats a subclass of \texttt{abc.ABC} with abstract members and a \texttt{typing.Protocol}
as explicit contracts. A base class whose methods only raise \texttt{NotImplementedError} is recorded
as an implicit contract but not flagged, because in Python this is usually a template method with
optional hooks. The Python flag also needs two signals, so width alone never flags. The Java and
Python ISP rates therefore measure different things and are not compared directly.

\subsection{Detector Validation}
\label{sec:python-validation}

The validation procedure is the one used for Java: 100 flagged and 100 unflagged entities per
principle, labelled by the same kind of reading judge against a written rubric, with a reason for
every label, every label traced to the file the judge was shown, the detector's verdict hidden, and a
mechanical audit before judging. Interface Segregation flags only 80 contracts in the Python corpus,
and all 80 flagged contracts were judged, so its precision is exact. For Dependency Inversion, 100 of
the 173 flagged pull requests were judged. Table~\ref{tab:py-validation} covers 980 judged entities.

Four of the five detectors are at least as precise in Python as in Java. Single Responsibility is the
exception.

\paragraph{Single Responsibility precision falls to a third.} The rubric is the same and it still
finds large classes. What differs is what a large Python class usually is. Most of the 89 false
positives are classes whose size comes from outside the project: a \texttt{transformers} model head,
a Home Assistant entity, a Lightning callback, a command class whose methods are the subcommands of
one tool. Others are clients for a single service or device, or configuration classes. In Python,
frameworks set the shape of many classes, so size says less about responsibility.

\paragraph{Liskov signals that a compiler would reject.} Of the 51 true positives, 46 of the 51 rest
on a signal that \texttt{javac} would reject: a removed parameter, an added required parameter or a
narrowed parameter type. Only five rest on refused bequest alone. Where no compiler removes these
faults, they make up most of the confirmed violations. This supports Finding~1: the Java detector's
three signals reflect what Java had already excluded.

\paragraph{Dependency Inversion.} The only systematic false positive in the Java census was a cycle
charged to a module declared as touched whose text had not changed. The Python judging rule checks
this directly by comparing each charged module's text in the two trees, and all 100 judged Python
flags passed: each closes a new import cycle through changed code, and no judged unflagged request
does. The most common form is a new or edited module that imports its own package root while the
root imports it back. The validation shows that the cycles exist, not that they are harmful, so the
Python cycle results below mean ``introduced an import cycle''.

\paragraph{Precision by agent.} Table~\ref{tab:py-validation-agent} gives precision by agent. The
Open/Closed flags, which carry the agent difference that survives adjustment, are confirmed most
often for Claude Code, so that difference does not come from noisier flags. The Liskov column is
uneven for another reason: two Claude Code pull requests contribute 50 of the 100 flagged rows, one
with 14 true positives in 30 and one with none in 20. Without those two requests, Liskov precision is
0.740.

\textbf{Change size dominates again.} Each doubling of the files a pull request touches roughly
doubles the odds of a flag, with odds ratios from 2.01 to 2.18 on all five principles ($p < 10^{-4}$),
against 1.88 to 1.95 in Java. It is the largest effect in both languages.

\textbf{The Open/Closed agent difference replicates.} Claude Code's odds of an Open/Closed flag are
2.09 (1.44--3.04) times Copilot's at the same size and time, with $p = 0.0001$, against 2.22
(1.21--4.07) in Java. The Python model tests ten agent coefficients, so the Bonferroni threshold is
$0.05/10 = 0.005$, and this coefficient passes it. Together with the Java estimate, this is the one
agent difference the study supports in both languages.

\textbf{A second difference is not confirmed.} Claude Code's odds of introducing an import cycle are
1.88 times Copilot's (1.17--3.03, $p = 0.0096$); in Java the ratio was 1.29 with an interval that
includes 1. The Python $p$-value does not pass the Bonferroni threshold, and the Java estimate does
not support it, so it is reported as a possible difference that needs confirmation. All other agent
coefficients have intervals that include 1.

\textbf{Time.} The monthly coefficient is close to 1 for OCP, ISP, DIP and LSP, as in Java. The
pull-request-level Single Responsibility flag, which Java does not have, rises by 5\% per month
($p < 10^{-4}$) over a thirteen-month window. Because that flag has precision 0.110, this is a trend
in how often large classes are touched or created, not a demonstrated trend in responsibility
violations.

Here the languages differ. In Java, merged code was indistinguishable from code closed without
review. In Python, merged pull requests have a lower flag rate than the unreviewed, reviewed-then-closed

still have higher Open/Closed odds (odds ratio 1.57, 1.15--2.15, $p = 0.004$) and higher Liskov odds

widens the gap. Because most unmerged requests were never reviewed, the result means that merged
Python code is structurally cleaner than abandoned code, not that reviewers rejected code for its
structure.

\label{sec:python-refinements}

numeric one (Interface Segregation restricted to 30 or more members) did not. Both rules were fixed
on Java data before any Python label existed, so applying them unchanged to the Python labels is a
holdout in a second language (Table~\ref{tab:py-refinements}).
