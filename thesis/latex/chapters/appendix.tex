\chapter{Pipeline Run Order and Reproducibility}
\label{app:pipeline}

This appendix lists the exact stage order used to reproduce the results reported in
Chapter~\ref{ch:results}. Every stage is resumable and checkpointed; re-running a stage after a
threshold change requires deleting that stage's output parquet first, since resumption otherwise
keeps previously-computed rows.

\footnotesize
\begin{verbatim}
curate.py --lang java      -> gold set        6,956 PRs / 1,010 repos,
                                              balanced on agent x outcome
clone_and_extract.py       -> file lists      GitHub API where local
                                              history is insufficient
mvn -o package (sidecar)   -> facts jar       JavaParser + SymbolSolver
run_java.py                -> five parquets   one parsed tree feeds all
                                              five principles; 4,245 ok
   (thresholds calibrated from corpus percentiles, then parquets
    deleted and the pass re-run, so no flag predates its threshold)
report_java.py             -> per-agent and per-outcome summaries
make_java_labeling_sample.py  -> 100 flagged + 100 unflagged per principle
extract_java_label_batches.py -> the source shown to the judge
audit_label_batches.py     -> GATE: every row must trace to that source,
                              and no batch may leak the detector's verdict
score_labels.py            -> precision and recall per principle,
                              per agent, per outcome
run_crosscheck_java.py     -> CK, PMD, DesigniteJava over the same trees
verify_v2_java.py          -> whole-corpus invariants; exits non-zero
                              on any failure
\end{verbatim}
\normalsize

A single combined delta pass (\texttt{run\_java.py}) computes all five principles from one parsed
tree, since parsing costs 10--20 seconds per tree and five separate harnesses would each pay that
cost independently. Extracted facts are cached by the content hash of the tree, so re-running
cannot silently change an input.

The Python replication (Section~\ref{sec:python}) follows the same order with a different extractor
and its own calibration. Label files carry a \texttt{py2\_} prefix and every label tool is called
with \texttt{--lang py2}, so no Python label can be written into the finished Java study.

\footnotesize
\begin{verbatim}
curate.py --lang py        -> gold set        7,050 PRs / 3,974 repos,
                                              balanced on agent x outcome,
                                              stratified by repository
clone_and_extract.py       -> file lists      same recovery as Java
run_python.py --calibrate  -> all metrics, flags switched off
propose_py_thresholds.py   -> thresholds near the 90th percentile,
                              written to config and re-imported
   (calibration parquets deleted before the flagged pass)
run_python.py --shard i/6  -> five parquets   repository-disjoint shards,
merge_py_shards.py            merged under six refusal checks; 4,946 ok
report_python.py           -> per-agent and tier-matched outcome summaries
fit_mixed_model.py --lang py  -> the joint model, all five principles
make_py2_labeling_sample.py   -> 100 flagged + 100 unflagged per principle
                                 (ISP: all 80 flagged, a census)
extract_py2_label_batches.py  -> the source shown to the judge
audit_label_batches.py --lang py2  -> the same GATE as Java
score_py2_labels.py        -> precision, stratum-weighted recall,
                              per agent, per outcome, PR clustering
py2_cross_language.py      -> the Java results tested in Python
\end{verbatim}
\normalsize

\section*{The Label Judge}
\label{app:judge}

Every other component of this pipeline is deterministic: the same tree produces the same facts, the
same facts produce the same flags, and the fact cache is keyed by the content hash of the tree. The
label judge is the one exception, and because the study's central methodological claim is
reproducibility, its configuration belongs on the record rather than in a footnote.

\textbf{What the judge is.} A large language model of the Claude family, reading the source of one
entity at a time and returning a binary verdict together with a written reason. Java judging ran
between 5 and 8 September 2026 and Python judging on 14 September 2026, each under a written rubric
fixed before judging began. Every borderline Python decision was recorded as a numbered precedent
and applied to later rows, so that the standard is stated rather than remembered. The judge is not
a pipeline stage: it computes no reported metric, and its
output enters the study only as the reference labels in Section~\ref{sec:instrument-validation}.

\textbf{What it was shown.} For each sampled entity, the extractor renders a batch file containing
the entity's own source and, where the principle is relational, the source of the other end: the
base method beside the override for Liskov, the contract beside each implementer for Interface
Segregation. \textbf{The detector's own verdict is removed} from that material, so agreement cannot
be inflated by anchoring, and the audit gate refuses to let judging begin if any batch still
carries it.

\textbf{What was required of a label.} Labels are written only through
\texttt{record\_labels.py}, which refuses a row whose source file is not on disk, refuses a verdict
that is not boolean, and refuses a label with no written reason. Every one of the 1{,}495 Java and
980 Python labels therefore carries a reason recorded at the time of judging, and the reasons are
stored beside the verdicts in the sample CSVs.

\textbf{A consistency check on the judge's standard.} The Python samples are shuffled before
judging, so the positive rate in the first half of each stratum should match the second. Four
principles pass. For Interface Segregation the flagged stratum reads 0.513 against 0.341; every
flagged row was re-read against the recorded precedents, no rule was found to have been applied
differently, and the gap traces to three contracts that occur twice, from forked or sibling
repositories, all in the first half. No label was changed.

\textbf{What cannot be reproduced exactly.} A language model is not a deterministic function of its
input, so re-running the judge would not reproduce every label character for character. Two
things bound that. The sampling is seeded and recorded, so the same rows are drawn every time. And
judge self-consistency was measured rather than assumed: 174 Java entities were judged in both rounds,
and the two independent readings agree on 89.7\% of them, which places a ceiling on how precisely
any agreement figure in this thesis can be known. The cross-check against CK, PMD and
DesigniteJava exists precisely because that ceiling cannot be raised from inside the judge.

\textbf{The conflict of interest.} The judge belongs to the same model family as one of the three
agents under evaluation. Section~\ref{sec:instrument-validation} tests for the leniency this could
produce, and reports the result there rather than here; the Python per-agent precision is given in
Table~\ref{tab:py-validation-agent}.

\section*{Software and Data Availability}

The corpus is derived from the public AIDev dataset \citep{li2025aidev}. The analysis pipeline, its
configuration and the result tables are version-controlled. No proprietary code, personal data or
human-participant data was collected or is distributed as part of this work.

\section*{Configuration Discipline}

All thresholds, file paths, and policy knobs (agent PR caps, star and license floors, rubric
cut-points, suppressor toggles) live in a single, heavily-commented configuration module per
language, so that a threshold change is a one-line, auditable edit rather than a scattered one.
Every pure evaluator module carries an inline self-check, a small hand-built example with a
known answer, run whenever that module changes, which is the closest analogue this pipeline has
to a unit-test suite, chosen deliberately over a conventional test framework so that the check
travels with the module it verifies.
