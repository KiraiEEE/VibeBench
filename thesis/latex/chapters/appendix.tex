\chapter{Pipeline Run Order and Reproducibility}
\label{app:pipeline}

This appendix lists the order in which the stages were run to produce the results in
Chapter~\ref{ch:results}. Every stage can be resumed. After a threshold change, the stage's output
Parquet file must be deleted before rerunning, because resumption otherwise keeps rows computed with
the old threshold.

\footnotesize
\begin{verbatim}
curate.py --lang java      -> gold set        6,956 PRs / 1,010 repos,
                                              balanced on agent x outcome
clone_and_extract.py       -> file lists      GitHub API where local
                                              history is insufficient
mvn -o package (sidecar)   -> facts jar       JavaParser + SymbolSolver
run_java.py                -> five parquets   one parsed tree feeds all
                                              five principles; 4,245 ok
   (thresholds calibrated from corpus percentiles, then parquets
    deleted and the pass re-run, so no flag predates its threshold)
report_java.py             -> per-agent and per-outcome summaries
fit_mixed_model.py         -> the joint model
make_java_labeling_sample.py  -> 100 flagged + 100 unflagged per principle
extract_java_label_batches.py -> the source shown to the judge
audit_label_batches.py     -> GATE: every row must trace to that source,
                              and no batch may show the detector's verdict
score_labels.py            -> precision and recall per principle,
                              per agent, per outcome
run_crosscheck_java.py     -> CK, PMD, DesigniteJava over the same trees
verify_v2_java.py          -> whole-corpus invariants; exits non-zero
                              on any failure
\end{verbatim}
\normalsize

One combined pass (\texttt{run\_java.py}) computes all five principles from a single parse of each
tree. Extracted facts are cached by the content hash of the tree, so a rerun cannot silently use a
different input.

The Python replication (Section~\ref{sec:python}) follows the same order with its own extractor and
calibration. Its label files carry a \texttt{py2\_} prefix, and every labelling tool is called with
\texttt{--lang py2}, so a Python label cannot be written into the Java study.

\footnotesize
\begin{verbatim}
curate.py --lang py        -> gold set        7,050 PRs / 3,974 repos,
                                              balanced on agent x outcome,
                                              stratified by repository
clone_and_extract.py       -> file lists      same recovery as Java
run_python.py --calibrate  -> all metrics, flags switched off
propose_py_thresholds.py   -> thresholds near the 90th percentile,
                              written to config and re-imported
   (calibration parquets deleted before the flagged pass)
run_python.py --shard i/6  -> five parquets   repository-disjoint shards,
merge_py_shards.py            merged under refusal checks; 4,946 ok
report_python.py           -> per-agent and tier-matched outcome summaries
fit_mixed_model.py --lang py  -> the joint model, all five principles
make_py2_labeling_sample.py   -> 100 flagged + 100 unflagged per principle
                                 (ISP: all 80 flagged, a census)
extract_py2_label_batches.py  -> the source shown to the judge
audit_label_batches.py --lang py2  -> the same GATE as Java
score_py2_labels.py        -> precision, stratum-weighted recall,
                              per agent, per outcome
py2_cross_language.py      -> the Java results tested in Python
verify_thesis_numbers.py   -> every headline number in the thesis
                              recomputed from the data
\end{verbatim}
\normalsize

\section*{The Label Judge}
\label{app:judge}

Every other component of the pipeline is deterministic: the same tree gives the same facts and the
same facts give the same flags. The label judge is the exception, so its configuration is recorded
here.

\paragraph{What the judge is.} A large language model of the Claude family that reads the source of
one entity at a time and returns a binary label with a written reason. Java judging took place
between 5 and 8 September 2026 and Python judging on 14 September 2026, each under a written rubric
fixed before judging began. Each borderline Python decision was recorded as a numbered precedent and
applied to later rows. The judge computes no reported number; its labels enter the study only as the
reference for Section~\ref{sec:instrument-validation}.

\paragraph{What it was shown.} For each sampled entity, the extractor writes a batch file with the
entity's source and, for relational principles, the source of the other side: the base method next
to the override for Liskov, the contract next to each implementer for Interface Segregation. The
detector's verdict is removed from this material, and the audit refuses to start judging if any batch
still contains it.

\paragraph{What a label must contain.} Labels are written only through \texttt{record\_labels.py},
which refuses a row whose source file is missing, a label that is not boolean, and a label without a
reason. All 1{,}495 Java and 980 Python labels therefore carry a reason recorded at judging time, and
the reasons are stored with the labels in the sample files.

\paragraph{A consistency check.} The Python samples were shuffled before judging, so the share of
positive labels in the first and second half of each stratum should be similar. Four principles meet
this. For Interface Segregation the flagged stratum reads 0.513 in the first half against 0.341 in the
second. Every flagged row was read again against the recorded precedents and no rule had been applied
differently; the gap comes from three contracts that each occur twice, from forked or related
repositories, all in the first half. No label was changed.

\paragraph{What cannot be reproduced exactly.} A language model is not a deterministic function of
its input, so judging again would not reproduce every label. Two things limit the effect. The
sampling is seeded, so the same rows are drawn every time. And for Java, 174 entities judged twice
agree on 89.7\%, which bounds the accuracy of any agreement figure. That comparison uses
the first labelling round, which was discarded as a source of results because its provenance could
not be audited: 294 of its Interface Segregation labels belonged to rows whose batch file did not
exist, and 200 more were written at about three seconds each. Those labels measure the judge's
stability here and contribute to no reported rate; the guards described above exist because of that
round. The comparison with CK, PMD and DesigniteJava provides a check that does not depend on the
judge at all.

\paragraph{Conflict of interest.} The judge belongs to the same model family as one of the three
agents. Section~\ref{sec:instrument-validation} tests for leniency towards that agent; the Python
per-agent precision is in Table~\ref{tab:py-validation-agent}.

\section*{Software and Data Availability}

The corpus is derived from the public AIDev dataset \citep{li2025aidev}. The pipeline, its
configuration, the result tables and the labels are under version control. No proprietary code,
personal data or human-participant data was collected or is distributed.

\section*{Configuration}

All thresholds, file paths and policy settings (agent sets, star and licence filters, rubric
thresholds, suppressor switches) are defined in one commented configuration module, so a threshold
change is a single edit. Each pure detector module has a self-check, a small example with a known
answer that runs when the module is executed as a script; the pipeline uses these instead of a
separate test framework.
