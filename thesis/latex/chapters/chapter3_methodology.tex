\section{Research Design Overview}
\label{sec:design-overview}

This study uses a \textbf{quantitative empirical benchmark design} to measure how well the code
produced by AI coding agents adheres to established object-oriented design principles. The unit of
analysis is the \textbf{merged pull request}, a real, self-contained change an agent made to a
real project, and the object of measurement is \textbf{SOLID adherence}, assessed one principle
at a time with deterministic, reproducible tooling and then validated against an independent
reading judge.

The study proceeds in two phases. The first, reported in Chapter~\ref{ch:literature}, is a
structured review of the literature on AI-assisted code generation, autonomous coding agents, and
software-quality measurement, which situates the research questions and identifies the gap this
thesis addresses. The second, described in this chapter and implemented in
Chapter~\ref{ch:results}, is the empirical evaluation itself, carried out over a curated corpus of
agent-authored pull requests drawn from the \textbf{AIDev dataset} \citep{li2025aidev}.

Three scoping decisions define the study and are defended below and in Section~\ref{sec:validity}:

\begin{enumerate}
  \item \textbf{Real pull requests rather than freshly generated repositories.} Generating new
  multi-agent codebases at evaluation scale is expensive in API cost and operationally complex, and
  it produces synthetic tasks of uncertain ecological validity. Measuring code the agents actually
  submitted to real projects trades experimental control for realism, and, because a pull
  request \emph{is itself} a completed unit of work, it lets us attribute a measurement to a
  specific agent action.
  \item \textbf{All three outcomes, not merged code only.} A merged pull request has passed human
  review, so a merged-only corpus measures the joint output of the agent and its reviewers. The
  corpus therefore carries \textbf{merged}, \textbf{rejected} (closed without merging) and
  \textbf{open} requests, balanced as far as the data allows on agent $\times$ outcome. This is
  what makes the review filter observable rather than invisible, and it is the single largest
  methodological difference between this design and a conventional mined-corpus study.

  One consequence has to be stated wherever the contrast is used: \emph{rejected} is not
  \emph{refused on quality}. Only the requests carrying an explicit maintainer objection
  (\texttt{changes\_requested}) or a completed review that ended in closure
  (\texttt{reviewed\_then\_closed}) express a judgement about the code; the majority of closed
  requests are superseded, stale or abandoned. The outcome axis is therefore reported by stratum,
  never as a single rejected-versus-merged number.
  \item \textbf{Java as the language of measurement.} SOLID is a set of object-oriented design
  principles, and a sceptic can reasonably argue that measuring it in a language that does not
  \emph{mandate} object orientation says more about the language than about the agent. Java removes
  that escape, classes are compulsory, \texttt{interface} is unambiguous, \texttt{@Override} is
  explicit and subtyping is nominal, so a finding that survives there is not an artefact of
  permissive syntax. The framework is language-parameterised (Section~\ref{sec:language-availability});
  a further language is an additional fact extractor rather than a second study.
  \item \textbf{Deterministic proxies validated against a reading judge.} Every reported quality
  number is produced by a pure, re-runnable program; a large language model is used \emph{only} to
  read the actual source and label a validation sample, never to compute a score. All agreement
  figures are therefore \textbf{rubric-versus-judge agreement}
  (Section~\ref{sec:reading-judge}, Section~\ref{sec:construct-validity}).
\end{enumerate}

The design is \textbf{cross-sectional} at the level of each PR: for the four ``architecture''
principles it compares the repository state immediately before and immediately after the change
(Section~\ref{sec:delta-harness}); for the single-responsibility principle it evaluates the touched files
at the merge commit. It does not track an agent's behaviour over a long sequence of changes.

\subsection{Research Paradigm}

The study operates within a \textbf{post-positivist paradigm}: it seeks measurable, reproducible
signals of design quality while accepting that no static tool fully captures a semantic property
like ``responsibility'' or ``substitutability.'' Each measurement is treated as a \textbf{proxy}
for the underlying construct, and the gap between proxy and construct is quantified directly,
through precision and recall against the reading judge, rather than merely acknowledged in
prose.

\subsection{Study Type}

The study is observational rather than experimental: the pull requests were authored by agents
working on their own tasks, in repositories this study does not control, before any of them were
measured. Nothing here is a treatment assigned to a unit, so the design supports comparison and
description but not causal attribution, and Table~\ref{tab:study-type} records that scope
explicitly.

\section{Research Questions}
\label{sec:rqs}

%

\paragraph{RQ1, Adherence, differentiation, and outcome.}
\emph{Do modern AI coding agents differ in their adherence to the five SOLID principles on real
Java pull requests; where do those differences concentrate; and does structural quality differ
between the requests maintainers merged and the requests they turned down?}

This is the comparative question, and it has two axes. The first is between agents: across a
common, mix-controlled corpus, do agents leave measurably different structural footprints, and for
which principles is there a real signal at the level of a single change? The second axis is new to
this design and is the reason the corpus is built the way it is. A corpus of \emph{merged} pull
requests measures what maintainers accepted, which is not the same as what agents produced; any
quality claim drawn from it is filtered through human review and is therefore
survivorship-biased. Including rejected and still-open requests makes the filter itself
observable: if agent-authored structure is worse in the requests that were closed unmerged, the
merge decision is doing quality work, and a merged-only study would have silently inherited the
benefit of that work while attributing it to the agent.

\paragraph{RQ2, Measurability and construct validity.}
\emph{Can SOLID adherence be measured at repository scale with deterministic, reproducible
structural proxies; how faithfully do those proxies agree with an independent reading judge; and do
they agree with established, independently developed analysers run over the same code?}

SOLID principles are semantic; static metrics are not. RQ2 asks how far a purely structural
instrument can be trusted, and answers it not with argument but with per-principle precision and
recall against labels produced by a judge that reads the actual source. A second, independent axis
compares the class-level instrument against three published analysers (CK, PMD and DesigniteJava)
run over exactly the same source trees (Section~\ref{sec:validation-independent}). The two axes
fail differently: a reading judge can be wrong in the same direction as the rubric, whereas an
independently built tool cannot be wrong in \emph{our} direction by construction.

\paragraph{RQ3, Locus of risk.}
\emph{Is code-quality risk primarily intra-unit or inter-unit?}

RQ3 asks \emph{where} risk lives: inside a single unit, a class, a method, that one pull
request can author whole, or in a \emph{relation between units}, a dependency graph, an
interface and its implementers, an override chain, that a single pull request rarely authors on
both sides. The distinction matters practically, because it predicts which kinds of design damage
an agent can plausibly do in one contribution and which it cannot.

\section{Research Strategy}
\label{sec:strategy}

\subsection{A Benchmark over Real, Merged Pull Requests}

The strategy is a \textbf{benchmark-style empirical study}: a fixed corpus of agent-authored
changes is passed through a uniform, deterministic analysis protocol, and the results are compared
across agents. Rather than commission new agent runs, the study mines completed work, which has two
advantages: the code was accepted into a real project (ecological validity), and each PR is a
bounded unit that can be attributed to one agent. The corresponding cost is a loss of task-level
control, the study cannot hold the \emph{difficulty} of each agent's tasks constant, which is
handled through repository-mix controls (Section~\ref{sec:repo-mix}) and treated as a threat to validity
(Section~\ref{sec:validity}).

The corpus is drawn from AIDev, which records pull requests authored by autonomous agents across
more than 116,000 repositories. Because the agents are wildly imbalanced in that raw data, any
comparison \textbf{must sample} deliberately
rather than use raw counts, or a single agent would dominate every aggregate. The curation that
produces the working corpus is described in Chapter~\ref{ch:results} (Section~\ref{sec:dataset}).

\subsection{The Proxy Method: One Deterministic Evaluator per Principle}

Each SOLID principle is operationalised as a \textbf{pure function over source text}, a program
that takes the code (as a string, or as a \texttt{\{module: source\}} mapping) and returns a
structural measurement plus a flag, with no dependence on how the source was obtained and no
external environment. This ``pure evaluator'' convention is what lets the single-responsibility
evaluator run on individually-extracted files while the architecture evaluators reuse the same
machinery over whole before/after trees, without changing the interface. Every evaluator is
\textbf{deterministic}: the same
input yields the same output on every run and machine, which is the precondition for a benchmark's
reproducibility. The precise proxy for each principle, with equations, is given in
Section~\ref{sec:proxy-mapping} and implemented in Chapter~\ref{ch:results}.

\subsection{The Before/After Delta and the Head-State Inventory}
\label{sec:delta-harness}

For the four principles whose smell is a property of the wider system, Dependency Inversion,
Interface Segregation, Open/Closed, and Liskov Substitution, a single measurement of the
repository ``now'' cannot tell us what the \emph{agent} did. The evaluators therefore run a
\textbf{delta harness}: they reconstruct the repository at the merge commit's first parent (the
state just before the change) and at the merge commit (just after), analyse both, and report only
the \textbf{difference} the PR introduced, a new dependency cycle, a newly-widened interface, a
newly-incompatible override. This isolates the agent's contribution from pre-existing structure it
merely edited (Figure~\ref{fig:delta-harness}).

\begin{figure}[htb]
\centering
\input{figures/fig_delta_harness.tex}
\caption{The before/after delta harness. Both trees are read via \texttt{git archive} at the merge
commit and its first parent; only the \emph{difference} the pull request introduces is charged to
the agent.}
\label{fig:delta-harness}
\end{figure}

Two attribution decisions follow from that aim and are stated here because they materially change
what is measured. First, \textbf{authorship is separated from authorship-adjacent editing}: a class
the agent created is scored separately from a class it merely touched, because scoring the touched
set alone attributes the host repository's accumulated debt to the agent
(Section~\ref{sec:findings}, Finding 4). Second, for the relation-level principles a violation is
charged when \textbf{either} side of the relation sits in a touched file, so that an agent which
edits a base class or widens an interface is charged for the subclasses and implementers it breaks
in files it never opened (Section~\ref{sec:proxy-mapping}).

The delta harness surfaced a result developed in Chapter~\ref{ch:results}: for ISP, LSP, and
largely DIP, \textbf{single PRs almost never create the whole smell}, because a cross-unit smell
spans code the PR did not fully author. To retain the signal that does exist, each of these
evaluators also emits a \textbf{head-state inventory}, every interface, override pair, or
dependency edge that exists at the PR head, reported as context, clearly separated from the
per-PR delta.

\subsection{Validation by a Reading Judge}
\label{sec:reading-judge}

A structural flag is only useful if it agrees with a considered reading of the code. The pipeline's
scripts produce the flags, and a large language model (Claude) then acts as the \textbf{label
judge}: for each principle a stratified sample of flagged and unflagged items is drawn, and the
judge reads the \emph{actual source}, for LSP, the overriding method and its base method side by
side, and labels each as a genuine violation or not. The deterministic flag is then scored
against these labels, and every precision and recall figure in this thesis is agreement between the
rubric and that reading (the label column is named, e.g., \texttt{llm\_srp\_risk}, to keep the
provenance explicit). Labelling is blind: the judge sees the entity, its metrics and its source, but
not the rubric's verdict (Section~\ref{sec:construct-validity}).

One independent corroboration is worth recording: several of the strongest LSP true positives carry
the original developers' \emph{own} \texttt{\# type: ignore\ \ldots\ incompatible with supertype}
comments, the very violation the deterministic rule caught, already confirmed in the repository.

\subsection{High-Recall Screens, Suppressors, and the Validation Gate}

Three of the five proxies (SRP, OCP, LSP) begin as \textbf{high-recall screens}: their thresholds
are set to miss as few genuine violations as possible (recall $\approx$ 1.0), accepting that some
flags will be false alarms. Precision is then improved, where possible, by a \textbf{suppressor}
a secondary rule that removes a \emph{nameable class} of false positives without lowering recall
(the pattern is: keep the flag unless a specific, well-understood benign idiom is present).
Conceptual cohesion (C3) is the single-responsibility suppressor; a closed-type-set rule is the
open/closed suppressor; a four-idiom rule is the Liskov-substitution suppressor.

Every candidate change, a new threshold or a suppressor, is admitted only if it survives the same
test: it must raise precision on labelled data without costing recall, and the reason it works must
be nameable in advance rather than discovered by search. A restriction derived from reading false
positives is cheap to justify, because the mechanism is visible in the rows it removes. A parameter
found by trying values until the score improves is not, because nothing distinguishes it from
fitting noise.

That distinction is why the two refinements reported in Chapter~\ref{ch:results} are stated as
restrictions of an existing signal rather than as new ones. Because both were derived by reading
the false positives in a sample, scoring them on that same sample would report a fitted quantity as
if it were an estimate. Each was therefore re-scored on a \textbf{holdout}: a second sample of 200
entities drawn with a different seed, excluding every row judged in any earlier round, and judged
before its result was compared with the first. Section~\ref{sec:instrument-validation} reports what
survived and what did not.

\subsection{Controlling for Repository Mix}
\label{sec:repo-mix}

Because the corpus is mined rather than commissioned, an agent's aggregate can be distorted by
\emph{which} repositories it happens to work in, one large, messy repository can dominate an
agent's pooled rate. Every comparative result is therefore reported \textbf{twice}: pooled across
all of an agent's units, and \textbf{macro-averaged per repository} (the mean of per-repository
rates), together with the agent's top-repository share as a concentration warning. Where the two
disagree, the macro figure is treated as the more trustworthy, and ranking claims lead with it.

\subsection{Language Selection and the Unit-of-Analysis Precondition}
\label{sec:language-availability}

Three of the five proxies are \textbf{class-scoped}: the God-class rubric (SRP), the
interface-width and implementer-stub rule (ISP), and the override-versus-ancestor comparison (LSP).
A class-scoped instrument carries a precondition that is easy to overlook and fatal if unmet,
\emph{the corpus must actually contain classes}, and it must contain them densely enough that a
per-class rate is measuring the agent rather than sampling noise.

Java satisfies that precondition by construction, and this is the main reason it is the language
of the study rather than an incidental choice. A Java compilation unit must declare a type, so
every pull request that touches Java source touches a class. Each of the five
principles has an unambiguous syntactic home in the language: \texttt{interface} declares a
contract and nothing else, \texttt{@Override} marks a substitution relationship explicitly,
subtyping is nominal rather than structural, and the compiler itself rejects several of the
violations that other languages permit at runtime. A structural proxy in Java is therefore
measuring the construct the principle is about, rather than a distant correlate of it.

That last property produces a result in its own right, developed in Chapter~\ref{ch:results}:
\textbf{what a compiler enforces determines which violations are expressible at all}. Three of the
five signals used to detect Liskov violations in a dynamically typed language cannot occur in Java
code that compiles, because a changed parameter list is an overload rather than an override,
parameter types are invariant, and visibility cannot narrow. The Java instrument keeps only the
signals a type system cannot check. This is not a limitation of the port; it is a measurement of
where each language leaves the principle unguarded.

The framework is nonetheless \textbf{language-parameterised by design}. Only the fact-extraction
layer is language-specific: it turns source into a language-neutral record of types, members,
supertypes, imports and member accesses, and every detector, threshold-calibration step,
validation procedure and reporting path consumes that record rather than the source. A second
language is therefore an additional extractor, not a second study.

\section{Operationalising SOLID: Proxy-to-Principle Mapping}
\label{sec:proxy-mapping}

This section states, at the level of method, how each principle's semantic rule is turned into a
computable proxy and why the proxy is a faithful, if imperfect, stand-in. The exact
thresholds and code paths are in Chapter~\ref{ch:results}; the equations referenced here are
defined there and summarised in Table~\ref{tab:proxy-map}.

\begin{description}[leftmargin=1.4cm,style=nextline]
\item[SRP (Single Responsibility).] The forbidden smell is the \emph{God Class}, one class doing
several unrelated jobs. The proxy combines a \textbf{seven-metric size/complexity rubric} (class
lines of code, method count, weighted methods, per-method complexity and parameters, and a
cohesion metric, LCOM) with a \textbf{semantic cohesion signal, C3} (conceptual cohesion of
classes). A class is flagged when it crosses at least two thresholds \emph{and} its methods do not
share a common vocabulary (low C3). The proxy is faithful because a God Class is characteristically
both large \emph{and} internally incoherent; combining size with cohesion is what separates ``large
but single-topic'' (a legitimately big engine or test suite) from ``large grab-bag.'' Its ceiling is
genuinely semantic and is examined in RQ3.

\item[OCP (Open/Closed).] The forbidden smell is the type/tag \emph{switch statement} that must be
edited for every new variant. The proxy detects every dispatch chain over one subject's type or tag
(\texttt{instanceof} ladders, \texttt{getClass() ==\ \ldots} comparisons, and \texttt{switch}
statements over an enum or a tag value), flags those wider than a calibrated branch count, and
then \textbf{suppresses} chains over a \emph{closed} type set, one whose members are fixed by
the language or by an external specification. OCP is uniquely
\emph{delta-native}: because a merged PR is itself a requirements change, the harness can watch
directly whether the agent \emph{extended} code or \emph{modified} a closed conditional. The
closed-set suppressor encodes the actual principle, dispatching over a fixed, exhaustive set is
not the open-ended extension OCP guards against.

\item[LSP (Liskov Substitution).] The forbidden smell is an override that breaks substitutability: a
an inherited method that is \emph{refused}, a precondition strengthened by a new argument guard,
or a postcondition weakened by returning \texttt{null} where the base never does. The signature
faults a Liskov proxy must chase in a dynamically typed language are absent here by construction,
because \texttt{javac} rejects them: a changed parameter list is an overload, parameter types are
invariant, and visibility cannot narrow. The proxy therefore targets only what the compiler cannot
check, and is computed over the resolved type hierarchy, which is what makes a nominal-subtyping
language tractable without building each of the 1{,}010 repositories.

\item[ISP (Interface Segregation).] The forbidden smell is a \emph{fat interface} whose implementers
are forced to stub methods they do not need. The proxy inventories every interface (abstract-method
count = width) and every implementer (proportion of trivial stubs = stub ratio), and flags fat
interfaces together with forced-stub implementers. Width alone is not the flag: a wide interface all
of whose implementers use it fully is not a violation; the flag requires width plus evidence of
forced stubs.

\item[DIP (Dependency Inversion).] The forbidden smell is a high-level module depending on a
concrete detail, or a dependency \emph{cycle}. The proxy builds the internal import graph before
and after the PR (via Tarjan's strongly-connected-component algorithm \citep{tarjan1972scc}) and
flags a change that makes two modules newly mutually reachable, or that worsens the mean
\textbf{Martin distance} from the main sequence beyond a threshold; it also records whether new
dependencies point at abstractions or concretions. Cycle novelty admits several reasonable
operationalisations that differ by an order of magnitude, so the definition is reported beside
every DIP rate (Section~\ref{sec:findings}, Finding 2). Validation showed the two halves are not
equally trustworthy, the cycle signal is reliable, the distance signal noisy, which is itself
a finding (Section~\ref{sec:results}).

\item[Component zones (a descriptor, not a sixth principle).] The five proxies above all work below
the package, which leaves the architectural level of the research question unmeasured. A sixth
evaluator therefore places every package on Martin's abstractness/instability plane \citep{martin2003agile}
the zone of pain (concrete and stable), the zone of uselessness (abstract and depended on by
nobody), the main sequence between them, using the same $A$, $I$ and $D$ definitions the DIP
proxy already computes. It deliberately emits \textbf{no delta and no violation flag}: validation
showed that the distance metric is unreliable as a signal of \emph{change} (Section~\ref{sec:findings},
Finding 2), while the \emph{position} of a package remains a sound description of it. A package
whose coordinates are undefined, no classes, or no internal coupling, is reported as
unplaceable rather than as zero, since collapsing the two would file every class-free utility
package in the zone of pain (Section~\ref{sec:findings}, Finding 2).
\end{description}

\section{Validity}
\label{sec:validity}

Design decisions that protect validity are stated here; the residual threats that remain after
those decisions, and the boundaries of what may be concluded, are collected once in
Section~\ref{sec:limitations} rather than distributed through the results.

\paragraph{Internal validity.} Every measurement is produced by a deterministic program over source
text, so a reported number can be regenerated exactly from the corpus. Thresholds are calibrated
from percentiles of the corpus's own distribution \emph{before} any labelling, which prevents the
circularity of tuning a detector on the sample used to judge it. Structural change is attributed to
a pull request only through a before/after comparison of the two source trees, so a violation that
already existed cannot be charged to the agent that walked past it.

\paragraph{Construct validity.} SOLID principles are semantic and structural metrics are not, so
the gap between them is measured rather than assumed. Each detector is validated on a stratified
sample containing both flagged and unflagged entities, sampling only flagged entities can
measure precision but can never discover a missed violation, and every label is written by a
judge that reads the entity's actual source, with its reason recorded alongside the verdict. A
second axis compares the class-level instrument against three independently developed analysers
over the same trees (Section~\ref{sec:validation-independent}).

\paragraph{Statistical validity.} Counts are reported beside every rate, and every rate carries a
Wilson score interval, which behaves correctly for the small numerators that delta-level signals
produce. Rates are reported both pooled and as a macro average over repositories, and the
mix-controlled figure leads wherever the two differ, because a corpus in which one repository
supplies a large share of an agent's pull requests will otherwise report that repository's habits
as the agent's.

\paragraph{Reliability.} The pipeline is resumable and idempotent, the fact extraction is cached by
content hash so re-running cannot silently change an input, and each pure module carries a
self-check that runs as a script. The validation material is auditable after the fact: every judged
row must be traceable to the source file the judge was shown, and a mechanical audit enforces that
property rather than trusting it.

\section{Ethical Considerations}
\label{sec:ethics}

The study involves no human participants, personal data, or proprietary code. All repositories were
publicly accessible and permissively licensed at the time of collection, and are cloned and
redistributed unchanged only within those licences. Agent outputs were collected from the public
AIDev dataset. No model training was performed; the only model used is a large language model
acting as a reading judge during validation, applied to public source code.
