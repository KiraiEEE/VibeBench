\section{Overview}
\label{sec:ch4-overview}

This chapter applies the methodology of Chapter~\ref{ch:methodology}. It describes the corpus
(Section~\ref{sec:dataset}), the tools (Section~\ref{sec:toolchain}), the exact detector definitions
(Section~\ref{sec:proxies-detail}), the pipeline (Section~\ref{sec:pipeline}) and the validation
procedure (Section~\ref{sec:validation}). Section~\ref{sec:results} reports the Java results:
detector validation, agent differences, the locus of risk and the cross-cutting findings.
Section~\ref{sec:python} reports the results in Python. Limitations are collected in
Section~\ref{sec:limitations}.

The analysis code is written in Python and is deterministic. It needs \texttt{pandas},
\texttt{pyarrow}, \texttt{statsmodels} and the \texttt{git} client, plus a JDK for the Java fact
extractor; the Python fact extractor uses only the standard library. No step that computes a
reported number depends on a network service or a language model.

\section{Dataset}
\label{sec:dataset}

\subsection{Source}

The corpus is drawn from AIDev \citep{li2025aidev}, a collection of pull requests opened by
autonomous coding agents on public GitHub repositories, with repository and commit metadata. Two
properties of the release shaped the curation.

\begin{sloppypar}
First, the released tables describe different populations. \texttt{pull\_request.parquet} and
\texttt{repository.parquet} contain only a subset of repositories with more than 100 stars. The
complete tables are \texttt{all\_pull\_request.parquet} and \texttt{all\_repository.parquet}, and
all figures in this thesis come from them.
\end{sloppypar}

Second, file-level attribution is missing for some pull requests, and which agent is most affected
changes between releases. The curation therefore treats every agent the same way: when the dataset
has no file list for a pull request, the list is retrieved from the GitHub API.

\subsection{Curation}

Curation keeps pull requests that change Java source files, identified by file extension, so that
Java modules inside repositories with another primary language are included. Repositories must have
at least 25 stars and a permissive licence (MIT, Apache-2.0, BSD-2-Clause or BSD-3-Clause, ISC,
0BSD, Unlicense, CC0-1.0 or MPL-2.0).

collected). Within each agent, every eligible rejected and open pull request is included, and merged

\subsection{Agent Selection}
\label{sec:agent-selection}

The same three agents, Claude Code, GitHub Copilot and OpenAI Codex, are
used in both languages, so that every cross-language comparison has the same agents on both sides.
Cursor and Devin were excluded because they have too little Java: 94 eligible Java pull requests for
Cursor, 72.3\% of them from three repositories, and 6 for Devin. Google Jules was excluded because it
appears for the first time in this release of the dataset, so its attribution of pull requests has no
earlier release to be checked against.

\subsection{Reconstruction and Attrition}

tries four methods in order: (1) the merge commit and its first parent; (2) the pull request's own
commits; (3) the \texttt{refs/pull/N/head} reference and its merge base; (4) the base and head
commits reported by the GitHub API. The first method exists only for merged requests, so the
comparison between merged and unmerged code has to control for the method used.

The attrition affects the outcome comparison in two ways. The analysable share differs by outcome:
62.1\% of merged requests, 66.9\% of open requests and 56.8\% of rejected requests. The

largest repositories, where design problems have the most room to accumulate. The 2{,}540 requests
that changed no production Java lean towards configuration and documentation work. The same filters
apply to all three agents, so they do not bias the comparison between agents, but the rates in this
chapter describe repositories within the parsing limit.

An empty file list is accepted only when the GitHub API confirms it. An empty diff caused by a
retrieval failure is recorded as a failure, not as a request that changed nothing.

\subsection{Resolution Quality}
\label{sec:resolution}

The Java extractor resolves supertypes and imports from source alone, without building the project,
so types defined outside the repository cannot be resolved. The median share of resolved supertypes
per pull request is 87.0\% (10th percentile 37.8\%, 90th percentile 98.4\%), and 498 touched files
failed to parse. Resolution is similar across agents: Claude Code 86.2\%, Copilot 85.9\% and OpenAI
Codex 89.3\%.

Resolution falls below 50\% in 718 of the 4{,}245 pull requests, mostly in projects whose supertypes
come from frameworks such as Spring, Android or Jakarta. The Liskov and Interface Segregation
detectors, which need resolved hierarchies, undercount in these projects. An unresolved supertype
removes a candidate; it cannot create a false one. The affected rates are therefore lower bounds.

\section{Toolchain}
\label{sec:toolchain}

\subsection{Selection}

The tools had to run locally, for free, deterministically and without a GPU, so that the benchmark
can be repeated over about a thousand repositories. Many mature Java analysers need compiled code.
ArchUnit and \texttt{jdeps} read class files, SonarQube's Java analysis uses compiled classes, and
Error Prone runs inside the compiler. Building 1{,}010 repositories at the exact commit of each pull
request would require resolving historical dependencies for each one, which is slow, not
reproducible, and fails more often for older and larger projects.

The analysis is therefore source-only. Java facts are extracted with JavaParser and its symbol
solver, which resolves types from the source tree, and the five detectors are pure functions over
those facts. The cost is incomplete resolution (Section~\ref{sec:resolution}).

The language model used as the label judge \citep{zheng2023llmjudge} is not part of the pipeline. It
reads source code and writes labels; every number in this chapter is computed by a deterministic
program from those labels and the result files.

\paragraph{Symbol resolution.} A syntax-only parser such as tree-sitter is cheaper but not
sufficient here. It parses Java but does not resolve names, so two classes called \texttt{Node} in
different packages become one, and every relation built on them is wrong. In an earlier pilot built
on tree-sitter, the Interface Segregation detector found no contracts and the Liskov detector found
seven override pairs. Single Responsibility and Open/Closed are local properties that syntax can
decide, but Liskov Substitution, Interface Segregation and Dependency Inversion are relations between
types and require knowing which type is which.

JavaParser's type solver maps package \texttt{a.b.C} to the file \texttt{<root>/a/b/C.java}, so it must
be given the source root, not the repository root. On the Chronicle-Wire repository, rooting it at
the repository root lowered supertype resolution from 93\% to 17\%. The extractor therefore infers
source roots from each file's \texttt{package} declaration, which works for Maven, Gradle,
multi-module and flat layouts without a build file.

\paragraph{Coverage of existing tools.} CK, PMD and DesigniteJava all have size or God Class rules
that relate to Single Responsibility, and DesigniteJava also reports hierarchy smells related to
Liskov Substitution and cyclic dependencies related to Dependency Inversion. DesigniteJava's
\emph{Missing Hierarchy} and \emph{Unexploited Encapsulation} smells address conditional logic on
types, which is close to the Open/Closed detector; Section~\ref{sec:crosscheck-results} compares
them. None of the three tools has a smell or rule for Interface Segregation.

Deciding whether a dispatch chain ranges over an open set of variants, or whether an interface forces
its implementers to write stubs, requires linking declarations across files. Single-file linters do
not build such a graph, and compiler-based tools obtain it from a classpath. The source-only
extractor provides it without a build, which is what makes the OCP and ISP detectors possible here.

The hardware shaped four decisions.

\begin{itemize}
  \item Compiling the corpus would mean building two commits for each of 4,245 pull requests, 8,490

  of two commits around the merge commit, source trees are read with \texttt{git archive} instead of
  a checkout, and a compressed tree cache per repository and commit is shared by all detectors.
\end{itemize}

\section{Detectors, Thresholds and Equations}
\label{sec:proxies-detail}

Each detector is a pure function over extracted facts. This section gives the exact rules. All
thresholds are defined in one configuration module and were set from each corpus's own distribution
before the corresponding labels were collected.

None of the five principles can be observed directly. Each concerns intent: the reasons a module may
change, the variants a design expects, the promises a subtype makes. A static detector can only
observe a structure that a violation tends to leave behind. As Table~\ref{tab:principle-gap} shows,
each principle asks for something different from what is computed instead; the table also gives the
unit of measurement and the agreement of each detector with the reading judge (precision / weighted
recall, Section~\ref{sec:instrument-validation}). Every result in
Section~\ref{sec:results} is first a statement about the detector and only through it a statement
about the principle.

a flag matches a judge reading the same source.

\paragraph{Attribution for relation-level principles.} For LSP, ISP and DIP, a violation is charged
to a pull request when either side of the relation is in a touched file. Charging only the flagged
entity would miss an agent that edits a base class or widens an interface and so breaks subclasses or
implementers in files it did not open. With this rule, 81{,}235 override pairs and 20{,}705
contracts are in scope across the Java corpus. The rule changes which pull request a violation is
charged to, not how many violations exist.

\subsection{SRP: God Class Rubric with a Cohesion Suppressor}

A class receives one rubric hit for each of six thresholds it reaches: class length 362 lines,
weighted methods per class 45, 20 methods, a method with cyclomatic complexity 11, a method with 5
parameters, and LCOM 0.86 (for classes with at least four methods). Each threshold is the 90th
percentile of the distinct production classes in the Java corpus. A class is flagged
(\texttt{srp\_risk}) with at least two hits, and \texttt{srp\_risk\_strict} marks classes with three
or more.

\paragraph{Cohesion (LCOM).} Following LCOM4 \citep{hitz1995cohesion}, the detector builds a graph
with one node per method and an edge between two methods that use a common attribute or where one
calls the other. Constructors are excluded, because a constructor uses every attribute and would join
unrelated groups of methods into one component; in Python the same rule removes
\texttt{\_\_init\_\_}, \texttt{\_\_new\_\_} and \texttt{\_\_post\_init\_\_}. With $c$ connected
components and $n$ methods, LCOM is normalised as
\begin{equation}
\text{LCOM} = \frac{c - 1}{n - 1},
\end{equation}
so 0 means one connected group and 1 means that no two methods are connected. On a synthetic class
with three separate responsibilities, the version that kept constructors scored LCOM\,=\,0; with
constructors excluded it scores the class as split.

LCOM is left undefined when the method graph can have no edges for syntactic reasons, for example
an interface whose methods have no bodies. Scoring such types would add a cohesion hit to types whose
only real signal is their number of methods. The test is made on the graph and not on the keyword,
so an interface whose default methods call one another keeps its value.

\paragraph{Conceptual cohesion (C3).} Following \citet{marcus2008c3}, each non-constructor method is
treated as a bag of identifier and comment terms, each bag becomes a TF-IDF vector, and C3 is the
mean cosine similarity over all pairs of methods:
\begin{align}
\cos(a,b) &= \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert} \\
C3 &= \operatorname*{mean}_{i<j} \cos(v_i, v_j)
\end{align}
where $v_i$ is the TF-IDF vector of method $i$. C3 is near 0 when methods share no vocabulary and
near 1 when all methods use the same terms. A class with exactly two hits and $C3 \geq 0.4$ is not
flagged, because its methods share one vocabulary. A class with three or more hits is flagged
regardless of C3.

\subsection{OCP: Dispatch Chain Length with a Closed-Set Suppressor}

The detector finds every dispatch chain, an \texttt{if}/\texttt{else if} ladder or a \texttt{switch}
that branches on one subject, and classifies it by what it tests: \texttt{instanceof} and comparisons
with a class literal or \texttt{getClass()} are type-based; \texttt{switch} on a value and on a tag
are tag-based. The Java result files contain 41{,}880 chain rows with at least two branches.

Thresholds were calibrated on distinct production chains before any label existed. Type-based chains
are flagged at three or more branches. Tag-based chains are flagged at eight or more, the 90th
percentile of value switches, because short value ladders are often parsers or state machines.

The closed-set suppressor removes dispatch over a set of values the language fixes:
\[
\text{smell} \;=\; (\text{branch count} \geq \text{threshold}) \; \wedge \; \lnot\,
\text{closed}(\text{subject}),
\]
where $\text{closed}$ holds when the subject's resolved type is an \texttt{enum}. A client cannot add
a value to an enumeration, so a switch over one is not the kind of growing conditional that OCP
targets. The rule suppresses 6{,}073 chain rows.

The rule recognises only sets that the language fixes. Many closed sets in this corpus are fixed by
external specifications instead, such as JDBC type codes, protobuf scalar types, Unicode blocks and
HTTP status classes, and the compiler sees them as open. Section~\ref{sec:future-work} proposes
recognising them.

\subsection{LSP: Override Compatibility over the Resolved Hierarchy}

In a dynamically typed language a Liskov detector must check that an override keeps its base's
signature. In Java the compiler does this: a method with a different parameter list is an overload,
parameter types cannot be narrowed, return types can only become more specific, and visibility cannot
be reduced. Code that compiles cannot contain these faults, so looking for them would only enlarge
the set of pairs examined. The Java detector looks instead at whether the override behaves like its
base.

For every pair of an internal subclass method and the nearest ancestor method with the same
signature, it computes three signals:

\begin{itemize}
  \item \texttt{refused\_bequest}: the base method has a working body and the override only throws
  \texttt{UnsupportedOperationException} or a similar refusal exception;
  \item \texttt{precondition\_strengthened}: the override adds argument checks that throw where the
  base accepted the call;
  \item \texttt{postcondition\_weakened}: the override can return \texttt{null} where the base never
  does.
\end{itemize}

Three exclusions apply. Constructors and static methods are excluded because they are not called
through a base-type reference. The five \texttt{Object} methods (\texttt{equals}, \texttt{hashCode},
\texttt{toString}, \texttt{clone} and \texttt{finalize}) are excluded because almost every class
declares them. And the base method must have a real body: a pair whose ancestor declares an abstract
or interface method has no inherited behaviour to refuse or to strengthen.

Section~\ref{sec:instrument-validation} shows that the three signals differ sharply in precision,
and that restricting the flag to refused bequest is the most effective single change made to any
detector in this study.

\subsection{ISP: Contract Width and Implementer Stub Ratio}

In Java a contract is an \texttt{interface} or an \texttt{abstract class}. The detector indexes both
across the whole repository and follows the resolved hierarchy, so members inherited from a
super-interface count towards the contract they impose. The Java result files contain 20{,}705
contract rows.

A contract is considered only if it has at least one abstract member and at least one implementer
inside the repository; otherwise every marker interface would count as a contract. For each contract
the detector records its width, the number of abstract members, and for each implementer its stub
ratio, the share of implemented members whose body is empty or only throws a refusal exception. A
contract is wide at 13 or more members, the 90th percentile of distinct contracts; 2{,}944 contract
rows reach this width, and 744 implementer rows carry forced stubs (at least two stubs forming at
least half of the implemented members). A pull request is flagged when it creates a wide contract,
widens one, or leaves an implementer with forced stubs. Width is a screen: a wide contract whose
implementers use every member is not a violation, which is why the stub ratio is recorded alongside
it.

\subsection{DIP: Import Graph Delta}

The detector builds the internal import graph of the whole repository before and after the pull
request and computes:

\begin{itemize}
  \item \textbf{Cycles}: strongly connected components with more than one module, found with
  Tarjan's algorithm \citep{tarjan1972scc}. A pair of modules $(u,v)$ is newly cyclic when $u$ and
  $v$ are mutually reachable after the change but not before, and the pull request is flagged when
  such a pair involves a touched file. Three definitions of a new cycle were implemented and gave
  counts that differ by an order of magnitude; all DIP rates in this thesis use this one. Attribution
  is by compilation unit, not by package. Filtering by package is too coarse for projects that keep
  most code in one package: in one Android project it admitted 44 newly cyclic pairs, of which only
  one involved a touched file.
  \item \textbf{Martin metrics} per package: instability $I = C_e / (C_a + C_e)$, abstractness
  $A = N_a / N_c$ and distance from the main sequence $D = |A + I - 1|$, where $C_e$ and $C_a$ are
  efferent and afferent couplings and $N_a$ and $N_c$ are the numbers of abstract and total classes
  \citep{martin2003agile}. The change in mean $D$ is recorded for every pull request but does not
  flag (Section~\ref{sec:zones-detail}).
  \item \textbf{Abstract dependency ratio}: the share of a touched module's new dependencies that
  point to modules defining an abstraction, recorded as context.
\end{itemize}

\subsection{Component Zones: a Package-Level Description}
\label{sec:zones-detail}

The five detectors work below the package. To describe the packages themselves, a sixth evaluator
places each package on Martin's abstractness and instability plane, using the metrics defined
above. As Figure~\ref{fig:martin-plane} shows, concrete, stable packages fall in the zone of pain
and abstract, unused packages in the zone of uselessness, and packages within 0.15 of the line
$A+I=1$ are on the main sequence.

\begin{figure}[htb]
\centering
\input{figures/fig_martin_plane.tex}
\caption{Martin's abstractness and instability plane.}
\label{fig:martin-plane}
\end{figure}

\begin{itemize}
  \item The zone of pain is the corner region of radius 0.5 around $(A{=}0, I{=}0)$: concrete and
  stable packages that many others depend on and that are therefore hard to change. The zone of
  uselessness is the region of radius 0.5 around $(1,1)$: abstract packages that nothing depends on.
  Packages within 0.15 of the line $A+I=1$ are on the main sequence, and the rest are intermediate.
  The radius and the band are presentation choices, stated so that a reader can change them.
  \item A package is unplaceable when a coordinate is undefined: $A$ for a package with no classes,
  $I$ for a package with no internal dependencies. Recording these as 0 would place every class-free
  utility package in the zone of pain.
\end{itemize}

The evaluator reads only the after tree and raises no flags. The distance from the main sequence was
tested as a signal of change in two validation rounds on earlier pilot corpora and was confirmed on
none of 17 flags: mean $D$ moves when files are added or moved, even when no dependency changes
direction. The position of a package on the plane is still a valid description of that package.
Treating a package in the zone of pain as a violation would need its own validation.

Packages are grouped by parent package, not by the first segment of the module name. A reverse-domain
prefix would place most of a repository in one package, which gives $C_e = C_a = 0$ and an undefined
$I$. The classifier has a self-check that includes the rule that an undefined coordinate never
produces a zone.

\section{Analysis Pipeline}
\label{sec:pipeline}

The pipeline is a sequence of resumable stages. Each stage reads the Parquet outputs of the previous
stage and writes its own, so any stage can be rerun alone. As Figure~\ref{fig:pipeline} shows, the
corpus stage samples agents and outcomes, the measurement stage recovers a before/after pair for
each pull request and scores all five principles from one parse, and the validation stage checks the
detectors against a reading judge and against three external analysers. The figure shows the Java
pipeline; the Python study follows the same stages with its own extractor
(Appendix~\ref{app:pipeline}).

\begin{figure}[htb]
\centering
\input{figures/fig_pipeline.tex}
\caption{The measurement pipeline.}
\label{fig:pipeline}
\end{figure}

The four delta detectors share one before/after tree pair per pull request, recovered by the four
methods of Section~\ref{sec:dataset}, read with \texttt{git archive}, parsed once and cached by
content hash. Each pull request is processed independently. Permanent outcomes are kept, temporary
failures are retried, and every attempt is recorded, so attrition can be audited.

\section{Validation Procedure}
\label{sec:validation}

For each principle a stratified sample is drawn: 100 entities the detector flagged and 100 it did
not, after the same production filter the report uses. The sampling seed is recorded. A class,
chain, override pair or contract that several pull requests touched is counted once, so that the
sample is not drawn towards entities many requests happen to touch. The deduplication keeps the
first observation of an entity, while the report keeps its largest observation; the two rules
disagree for 123 of the roughly 7{,}600 flagged Java classes (1.6\%), because a class can be flagged
in the tree of one pull request and not in another's. The judge reads
the source of each entity and writes a binary label (\texttt{llm\_<principle>\_risk}) and a reason;
for LSP it sees the overriding method next to its base method. The flag is scored against the label
as precision and recall, overall and per agent.

Thresholds for all five detectors were set from corpus percentiles before any label existed. Two
refinements were derived later from the false positives of the first sample: restricting the Liskov
flag to refused bequest, and requiring interface contracts of at least 30 members. Scoring a
refinement on the sample it was derived from overstates its precision. Both were therefore scored
again on a holdout: 200 further entities per principle, drawn with a different seed from the same
population, excluding every row judged before, processed through the same audit and judged with the
same rubric before the rounds were compared. Every earlier round is excluded, not only the most
recent one, because a sample that shaped a detector can no longer estimate its performance.

\subsection{A Second Check: Independent Analysers}
\label{sec:validation-independent}

For Java, three independently developed tools were also run on the same source trees and their
verdicts compared with the detectors'.

The comparison uses one tree per repository, the after tree of the repository's most recent pull
request, for a seeded random sample of 150 corpus repositories. CK 0.7.0 provides per-class metrics,
PMD 7.7.0 design rules and DesigniteJava 1.1.2 design smells. All three run with their default
thresholds, because tuning them towards agreement would defeat the purpose.

Three points matter for interpretation. First, agreement is reported symmetrically, with no tool
treated as ground truth, and the tools are also compared with each other. Second, CK's
\texttt{lcom} is LCOM1 and its \texttt{lcom*} is the Henderson-Sellers variant
\citep{hendersonsellers1996metrics}, while this study uses normalised LCOM4, so cohesion is compared
by rank correlation only. Third, each tool fails silently by writing an empty result, which would
read as a clean repository. The status of every tool on every repository is recorded, and failed
repositories are excluded from that tool's comparison.

Rank correlation is unaffected by monotone rescaling. A high Spearman correlation on a size metric
therefore shows agreement on ordering, not on scale.

\paragraph{Why recall is weighted.} Each sample is half flagged and half unflagged, but the
population is not. For Liskov it holds 574 flagged override pairs against 25{,}594 unflagged ones,
so one sampled unflagged pair stands for about forty-five times as many entities as one sampled
flagged pair. Treating the two strata as equally common would give a Liskov recall of 0.966;
weighting them gives 0.386. The intervals are wide because a weighted recall depends on the few
violations found in the unflagged stratum, three for Liskov in 200 rows, multiplied by a large
factor.

The population used for this weighting is the one the sample was drawn from: production entities,
counted once each (Section~\ref{sec:validation}). Weighting with the raw result rows instead, which
include test code and repeat a class once per pull request that touched it, would describe a
population the study does not report and would move four of the five figures, Interface Segregation
by almost nine points.

For SRP, OCP and DIP the detectors miss few violations and over-report many, so their flag rates are
upper bounds on what the judge would confirm. For LSP and ISP they are not: these detectors find the
violations with a clear structural form and miss the rest. The three Liskov violations found in the
unflagged stratum show what is missed. A Vaadin root node throws \texttt{IllegalStateException} for
any non-null parent where its base accepts any parent; a CommCare screen controller overrides a
method that disables a login button with an empty body; and an nd4j operation implements
\texttt{setY} as \texttt{this.y = null}, discarding its argument. None of them throws where the
detector looks, and one does nothing at all.

Precision is below 0.5 for four of the five detectors. A structural detector answers a question about
the shape of code, while the principles concern meaning, and these figures measure that gap.

\paragraph{Two divergences explained by the unit of measurement.} Agreement on substitutability is

138 cross-check repositories, and over the 63{,}326 production types they contain the two detectors

definition account for most of the gap. DesigniteJava requires that a hierarchy be available or
warranted before it reports the smell, whereas the detector fires on chain width alone once the
subject is not an enumeration; and DesigniteJava reports at the level of the abstraction that should
have existed, not the method body holding the chain. The reading judge, which does read the body,
scored this detector at 0.330 precision, close to the other three sampled principles. The Open/Closed
proxy therefore measures something narrower than the published smell, and it rests on the judge
alone.

\paragraph{Coverage.} DesigniteJava produced results for 141 of the 150 repositories, 92.1\% of this
study's types joined to a CK row, and PMD could not analyse 252 files. Types affected by a tool
failure are excluded from that tool's comparison.

\textbf{Change size is the strongest predictor.} Each doubling of the number of Java files a pull
request touches multiplies the odds of a flag by about 1.9 on all three principles ($p < 10^{-4}$).
No agent coefficient is as large or as certain.

\textbf{One agent difference remains after adjustment.} Claude Code's odds of an Open/Closed flag are
2.22 times Copilot's at the same size and time (1.21--4.07, $p = 0.010$). For Interface Segregation
and Dependency Inversion the odds ratios fall to 1.11 and 1.29 with intervals that include 1, so most
of the ordering in Table~\ref{tab:agent-rates} is explained by change size. No Codex coefficient is
significant.

The model tests six agent coefficients. With a Bonferroni correction the threshold is
$0.05/6 = 0.0083$, and the Open/Closed coefficient ($p = 0.010$) does not pass it on its own. The
effect is claimed because it replicates in the independent Python corpus, where $p = 0.0001$
(Section~\ref{sec:python-agents}).

\textbf{Time has no detectable effect.} The monthly coefficient is close to 1 on every principle
(1.00 to 1.03, all $p > 0.5$). Once size and repository are accounted for, when a pull request was
written does not predict whether it is flagged in this corpus and period.

The model does not make the design experimental. Agents chose their own tasks in repositories this
study does not control, so the coefficients are adjusted associations, not causal effects. A
difference in the kind of task each agent received would still appear in its coefficient. Adjusting
for size also removes any part of an agent difference that operates through the size of the changes
the agent chooses to make.

Codex introduced no refused-bequest violation in 770 pull requests, and only 16 of the 4{,}245 pull
requests introduced one. The detector does find such violations in the code these pull requests
touched (Section~\ref{sec:locus-of-risk}). The rate is low because a new violation requires writing a
base method and an override that contradict each other.

\subsection{Locus of Risk (RQ1)}
\label{sec:locus-of-risk}

For the relation-level principles a violation is charged to a pull request when either end of the
relation is in a touched file. Touched is not authored: a request that edits one line of a subclass
is charged with the override pair it belongs to. Only SRP separates authored from edited code. The
comparison below therefore gives an upper bound on how much of the relation-level risk the agents
could be responsible for.

A violation present in the code a pull request touched may have been written by anyone at any time.
A violation the pull request introduced is one the before/after comparison attributes to this
change. Table~\ref{tab:present-introduced} compares the two, with the flagged counts corrected by the
precision in Table~\ref{tab:validation}. Present counts are distinct production entities. For
LSP both columns use the refused-bequest flag (precision 1.000); for DIP the detector only records new
cycles, so both columns count the same pull requests.

After precision correction, between 0.4\% and 4.1\% of pull requests introduce a violation, depending
on the principle, in code that already contains hundreds to thousands of flagged entities. For Liskov
Substitution the touched code contains 183 refused-bequest relationships outside test and generated
code, and 16 pull requests introduced one.

The Liskov detector has the lowest recall of the five (0.386, 0.210--1.000, for the three-signal
flag), and it undercounts in the 718 pull requests with less than 50\% symbol resolution. Both
effects mean that more violations are present than counted, which would widen the gap between
present and introduced violations, not close it.

The explanation is structural. A Single Responsibility or Open/Closed violation lies inside one
class or one conditional, which a single pull request can write. A Liskov, Interface Segregation or
Dependency Inversion violation lies in a relation: a base and its override, an interface and its
implementers, a cycle among modules. One contribution rarely writes both ends, so these violations
build up over many changes and authors.

A consequence for practice is that review of one change at a time can catch problems inside a unit
but will rarely see problems between units. These require a view of the repository over time.

\subsection{Cross-Cutting Findings}
\label{sec:findings}

\paragraph{Finding 1: the type system limits which Liskov violations can be written.} Three of the
signals used to detect Liskov violations in a dynamically typed language cannot occur in Java code
that compiles: a changed parameter list makes an overload, parameter types are invariant, and
visibility cannot be reduced. The Java detector therefore uses only signals the compiler does not
check. Of those, refused bequest is correct on 31 of 31 flags, while the two behavioural signals are
correct on 6 of 36 and 3 of 33. The Python results test the other side of this result
(Section~\ref{sec:python-validation}).

\paragraph{Finding 2: width predicts Interface Segregation violations but not Open/Closed
violations.} Contract width separates Interface Segregation flags sharply
(Table~\ref{tab:isp-width}): precision is 0.071 for 18 to 29 members and 0.900 for 50 to 99. The
number of branches in a dispatch chain does not separate Open/Closed flags: as Table~\ref{tab:ocp-width}
shows for the validation sample, precision stays between 0.270 and 0.400 in every band.

\begin{table}[htb]
\centering
\caption{OCP precision by dispatch chain length.}
\label{tab:ocp-width}
\begin{tabular}{@{}lrrr@{}}
\toprule
\textbf{Branches} & \textbf{Flags judged} & \textbf{True} & \textbf{Precision} \\
\midrule
0--5     & 37 & 10 & 0.270 \\
6--9     & 23 &  9 & 0.391 \\
10--15   & 19 &  6 & 0.316 \\
16--30   & 10 &  4 & 0.400 \\
$\geq$31 & 11 &  4 & 0.364 \\
\bottomrule
\end{tabular}
\end{table}

The difference follows from the principles. Interface Segregation is violated by breadth, so width
measures it fairly directly. Open/Closed concerns whether a set of variants can grow. A 64-branch
switch over PostgreSQL type identifiers is closed, because a wire protocol fixes the set; a
five-branch switch over supported storage backends is open, because the next release may add one.
Counting branches cannot tell them apart.

\paragraph{Finding 3: the closed sets that matter are external specifications.} The Open/Closed
suppressor recognises sets fixed by the language, and it removed none of the 100 flagged rows in the
validation sample. The false positives show why: the closed sets in practice are fixed by external
specifications, such as JDBC type codes, protobuf scalar types, FHIR binding strengths, Unicode
blocks, AWT cursor constants and Android key codes, or by generated parser tables, where a 356-branch
keyword switch is generated from a grammar file. A suppressor that recognises such specification
enumerations is a concrete way to make the detector more precise.

\paragraph{Finding 4: most design problems in the touched code were already there.} After precision
correction, the Java code these agents touched contains about 2,600 Single Responsibility violations
and 183 refused-bequest relationships, while between 0.4\% and 4.1\% of pull requests introduced a
violation of a given principle. The difference is largest for the relation-level principles, for the
reason given in Section~\ref{sec:locus-of-risk}.

\paragraph{Finding 5: classes written by agents are flagged less often than the classes they edit.}
7.7\% against 13.5\% pooled, and 5.6\% against 20.9\% averaged over repositories
(Table~\ref{tab:authored-edited}). The two groups differ in age and size, so this describes the
corpus and does not show that agents write better classes than people. It does contradict the
assumption that agent code is the main source of structural problems in these repositories.

\paragraph{Finding 6: merged code is not a biased sample of unreviewed agent code.} With the
reconstruction method held constant, merged pull requests are structurally indistinguishable from
the 1{,}006 closed without review (Table~\ref{tab:outcome-stratum}). For these signals, merged-only
corpora are therefore usable. The two reviewed strata, with 36 and 135 requests, show higher rates on
Interface Segregation and Dependency Inversion, so whether reviewers act on structure is still an
open question that needs many more reviewed rejections.
